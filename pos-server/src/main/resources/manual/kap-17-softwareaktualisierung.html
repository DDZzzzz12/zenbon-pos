Kapitel 17 – Softwareaktualisierung

Ihre Kasse kann sich selbst auf neue Programmversionen hinweisen und diese vorbereiten. Jede Nacht um 03:00 Uhr schaut der Server nach, ob eine neuere Version veröffentlicht wurde (geplante Aufgabe Update Check). Bedient wird das Ganze im Web-Admin unter System → Software-Update.

Nachsehen ist eingeschaltet, Installieren nicht. Die nächtliche Prüfung läuft ab Werk – sie liest nur nach, was veröffentlicht wurde, und legt die Datei geprüft auf der Festplatte bereit. Installiert wird nichts, solange Sie den Schalter Updates automatisch installieren nicht selbst einschalten. So erfahren Sie von jeder neuen Version, ohne dass sich Ihre Kasse über Nacht ungefragt verändert.

Die drei Schritte

SchrittWas passiertWer löst ihn aus
Prüfen Der Server fragt nach der neuesten veröffentlichten Version. Es wird nichts heruntergeladen. Jede Nacht um 03:00 Uhr – oder per Schaltfläche Jetzt prüfen.
Bereitlegen Die neue Version wird heruntergeladen und ihre Prüfsumme kontrolliert. Stimmt sie nicht, wird die Datei verworfen. Während des Ladens zeigt die Karte einen Fortschrittsbalken mit den geladenen Megabyte, erst für das Server-Update, danach für die Kassen-App (Android). Der Balken erscheint auch dann, wenn der Download in der Nacht oder von einer anderen Seite aus gestartet wurde, und er endet von selbst – danach wird Jetzt installieren freigegeben. Ist die Gesamtgröße nicht bekannt, läuft der Balken ohne Prozentangabe. Automatisch im Anschluss an die nächtliche Prüfung – oder per Jetzt herunterladen.
Installieren Die bereitliegende Version wird eingespielt. Der Server startet dabei neu. Sie selbst per Jetzt installieren – nur mit eingeschaltetem Updates automatisch installieren auch nachts.

Die Karte oben auf der Seite sagt Ihnen jederzeit in einem Satz, wo Sie gerade stehen: aktuell, neue Version verfügbar, bereitgelegt, oder es gibt ein Problem. Darunter stehen die laufende Version, die verfügbare Version und der Zeitpunkt der letzten Prüfung.

Wie viel wird heruntergeladen?

Beim Bereitlegen wird in der Regel nur ein Bruchteil der neuen Programmdatei übertragen. Der Server setzt die neue Datei größtenteils aus der bereits installierten zusammen und lädt nur die Teile nach, die sich tatsächlich geändert haben.

Bevor die Datei bereitgelegt wird, prüft der Server die zusammengesetzte Datei gegen die veröffentlichte Prüfsumme. Nur wenn diese exakt stimmt, wird sie übernommen.

Klappt einer dieser Schritte nicht – etwa weil die Verbindung den teilweisen Abruf nicht unterstützt – lädt der Server automatisch die vollständige Programmdatei und legt sie wie bisher bereit. Sie müssen dazu nichts tun; das Bereitlegen dauert dann nur länger.

Am benötigten Speicherplatz ändert das nichts: Auch bei einem kleinen Download wird am Ende eine vollständige Programmdatei geschrieben – dazu die Sicherungskopie der bisherigen Version und die Datenbanksicherung.

Kanal und Zugangstoken

Es gibt zwei Bezugsquellen für neue Versionen. Welche für Sie die richtige ist, hängt davon ab, wie Ihre Kasse geliefert wurde – im Zweifel fragen Sie Ihren Betreuer, bevor Sie hier etwas umstellen.

KanalProgrammarchivFür wenZugangstokenTSE-Baustein enthalten
Öffentlich DDZzzzz12/zenbon-pos Die frei verfügbare Ausgabe des Programms. Wird nicht benötigt. Nein
Intern DDZzzzz12/POS-KMP Die interne Ausgabe für betreute Installationen. Erforderlich – ohne Token findet der Server nichts. Ja
Die öffentliche Ausgabe enthält den TSE-Baustein nicht. Der Hersteller-Baustein Ihrer technischen Sicherheitseinrichtung darf nicht frei weitergegeben werden und fehlt dort deshalb. Er wird bei einer Aktualisierung nie überschrieben – eingespielt wird ausschließlich das Programm selbst. Wenn Sie eine betreute Installation haben, bleiben Sie trotzdem auf dem internen Kanal: nur dort bekommen Sie die Ausgabe, die zu Ihrer Einrichtung gehört.

Ein Zugangstoken für den internen Kanal beschaffen

Das Token ist eine Art Ausweis, mit dem sich Ihre Kasse bei GitHub ausweist, um die interne Ausgabe lesen zu dürfen. Sie erstellen es einmalig im GitHub-Konto, das Zugriff auf das interne Programmarchiv hat:

  1. Bei GitHub anmelden und über das eigene Profilbild Settings → Developer settings → Personal access tokens → Fine-grained tokens öffnen.
  2. Generate new token wählen und einen Namen vergeben, an dem Sie später erkennen, wozu es gehört – z. B. den Namen Ihres Betriebs.
  3. Als Geltungsbereich nur das eine Programmarchiv auswählen, nicht alle Archive des Kontos.
  4. Als Berechtigung ausschließlich Contents: Read vergeben. Mehr braucht die Kasse nicht, und mehr sollte sie auch nicht bekommen.
  5. Eine Laufzeit wählen und das Token erzeugen. Es wird nur ein einziges Mal angezeigt.
  6. Im Web-Admin unter Software-Update → GitHub-Token in das Feld Neues Token einfügen und Token speichern anklicken.
Ein Token läuft ab. Notieren Sie sich das Ablaufdatum. Danach kann Ihre Kasse die interne Ausgabe nicht mehr lesen, und Sie sehen auf der Seite die Meldung, dass der Zugang abgelehnt wurde. Das ist ausdrücklich nicht dasselbe wie „alles aktuell“: ein abgelaufenes Token würde sonst jahrelang so aussehen, als gäbe es keine neuen Versionen. Legen Sie in diesem Fall einfach ein neues Token an und tragen Sie es ein.

Das gespeicherte Token wird nie wieder angezeigt – die Seite zeigt nur die letzten vier Zeichen, damit Sie erkennen, welches Token hinterlegt ist. In der Datenbank liegt es verschlüsselt.

Wenn die Installation abgelehnt wird

Vor jeder Installation prüft der Server, ob der Betrieb sie gerade verträgt. Ist das nicht der Fall, passiert nichts – und die Seite nennt Ihnen den Grund. Das gilt für beide Wege: für Ihren Klick auf Jetzt installieren ebenso wie für den nächtlichen Versuch. Nach einer abgelehnten Nacht steht am nächsten Morgen „Nächtliche Installation abgelehnt“ auf der Karte, mit dem jeweiligen Grund. Solange sich daran nichts ändert, wird auch die nächste Nacht abgelehnt.

GrundWas dahinterstecktWas zu tun ist
Offene Geschäftsvorfälle Seit dem letzten Kassenabschluss sind noch Rechnungen oder Einträge im Kassenbuch einer fiskalen Kasse (Ladenkasse) offen. Nicht-fiskale Bücher, z. B. ein Tresor, zählen nicht. Tagesabschluss (Z-Bon) machen.
Offener Tisch Mindestens ein Tisch ist noch nicht abgerechnet. Alle Tische abrechnen oder stornieren.
Offener TSE-Vorgang Die technische Sicherheitseinrichtung hat noch eine nicht abgeschlossene Transaktion. Den zugehörigen Vorgang an der Kasse beenden. Bleibt es dabei, siehe Kapitel 14 – Compliance.
Ein anderer Auftrag läuft Zeitgleich läuft z. B. eine Datensicherung oder ein Export. Nichts – einfach etwas später erneut versuchen.
Zu wenig Speicherplatz Auf der Festplatte ist nicht genug Platz für Programm und Sicherung. Platz schaffen – alte Sicherungen und Exporte auslagern – und es dann erneut versuchen.
Die bereitgelegte Datei bleibt liegen. Eine abgelehnte Installation wirft den Download nicht weg. Ein Betrieb, der abends spät schließt, lädt also nicht jede Nacht dieselben Daten erneut herunter – sobald der Grund wegfällt, kann sofort installiert werden.

Was bei der Installation passiert

  1. Die bereitgelegte Datei wird geöffnet und das neue Programm entnommen.
  2. Es wird eine Sicherung der Datenbank angelegt – immer, ohne Ausnahme. Lässt sie sich nicht schreiben, bricht die Installation ab und es wird nichts verändert.
  3. Das alte Programm wird beiseitegelegt, das neue eingesetzt.
  4. Der Server startet neu. Das dauert typischerweise unter einer Minute; in dieser Zeit sind Kassen und Web-Admin nicht erreichbar.
  5. Nach dem Neustart prüft der Server selbst, ob die neue Version sauber hochgekommen ist, und vermerkt das Ergebnis.
Der Neustart ist der Grund für die ganze Vorsicht. Deshalb wird während des laufenden Betriebs nicht installiert, deshalb läuft die nächtliche Automatik um 03:00 Uhr, und deshalb wird bei offenen Tischen oder offenem Kassenbuch abgelehnt. Installieren Sie von Hand daher am besten nach dem Tagesabschluss und nicht mitten im Service.

Bricht die Verbindung genau in dem Moment ab, in dem Sie Jetzt installieren gedrückt haben, ist das kein Fehler: der Server beendet sich in genau diesem Augenblick. Warten Sie den Neustart ab und laden Sie die Seite neu.

Verschlüsselte Verbindung (HTTPS)

Kassen, Bestellstationen und Browser erreichen den Server nur über HTTPS. Davor läuft Caddy (ein vorgeschaltetes Programm, das die Verschlüsselung übernimmt), das das Installationsskript mit einrichtet. Der POS-Server selbst lauscht nur noch auf dem Serverrechner (127.0.0.1:8080 bzw. dem im Einrichtungsassistenten gewählten Port).

Ablauf

  1. Das vollständige Server-Paket dieser Version herunterladen und entpacken.
  2. Nach dem Tagesabschluss das Installationsskript auf dem Server ausführen und die Frage Start now? (y/N) mit y beantworten.
  3. Das Stammzertifikat auf alle Geräte verteilen und dabei den Fingerabdruck vergleichen.
  4. Die Kassen aktualisieren.
  5. An jeder Kasse die neue https://-Adresse eintragen. Die vorbelegte Adresse vor dem Speichern prüfen: die IP-Adresse ohne Port oder einen lokalen Namen (falls eingerichtet) verwenden (siehe Kapitel 16). Bereits gekoppelte Android-/Linux-Kassen müssen dabei nicht neu gekoppelt werden: Im selben Bildschirm („Serveradresse muss HTTPS verwenden“) den Zertifikat-Prüfcode aus dem Back Office eingeben (Terminals › Kopplungscode erzeugen); die Kasse lädt das Zertifikat, prüft es und behält ihre Kopplung. Zeigt eine Kasse später „Server nicht erreichbar“ mit dem Feld „Zertifikat-Prüfcode“, genügt dort dieselbe Eingabe („Zertifikat vertrauen“).
Reihenfolge beim Update auf diese Version: zuerst das Installationsskript auf dem Server erneut ausführen, danach die Kassen aktualisieren. Die automatische Aktualisierung tauscht nur das Serverprogramm und kann Caddy nicht einrichten. Laden Sie dazu das vollständige Server-Paket dieser Version herunter und starten Sie das Skript aus dem entpackten Ordner (er enthält den Unterordner caddy). Daten, Schlüssel und Zertifikate bleiben dabei erhalten. Kassen dieser Version akzeptieren keine http://-Adresse mehr: sie zeigen „Serveradresse muss HTTPS verwenden“ und erreichen den Server erst, wenn Caddy dort läuft.

Zwischen beiden Schritten arbeitet keine Kasse. Sobald das Skript gelaufen ist, erreichen noch nicht aktualisierte Kassen den Server nicht mehr. Führen Sie das Skript deshalb nach dem Tagesabschluss aus und aktualisieren Sie die Kassen direkt danach.
Port angeben, falls geändert. Caddy leitet an 127.0.0.1:<Port> weiter. Haben Sie im Einrichtungsassistenten einen anderen Port als den Standard gewählt, geben Sie genau diesen dem Skript mit – als zweites Argument nach dem Installationsverzeichnis. Die Ports 80 und 443 sind dafür nicht zulässig, sie belegt Caddy.

Beispiel für Port 8090:

sudo ./install-service.sh /opt/pos-server 8090

Zertifikate (lokale Zertifizierungsstelle)

sudo ./install-service.sh

Caddy stellt die Zertifikate selbst aus – für https://localhost, die aktuellen IPv4-Adressen des Servers, https://<Rechnername>.local und die lokalen Namen (siehe Lokaler Name). Der Server braucht dafür keinen Internetzugang. Das Skript legt das Stammzertifikat als pos-root-ca.crt ab (Ablageort siehe Tabelle unten) und zeigt seinen SHA-256-Fingerabdruck.

Beantworten Sie am Ende die Frage Start now? (y/N) mit y. Erst beim ersten Start erzeugt Caddy das Stammzertifikat; sonst fehlen Datei und Fingerabdruck, bis Sie das Skript erneut ausführen und mit y antworten.

Die Adressen für die Kassen stehen in der Zeile Local-CA sites: der Skriptausgabe (z. B. https://192.168.1.10). Die IP-Adresse zeigt auch hostname -I. Auf Android-Kassen die IP-Adresse oder einen lokalen Namen statt des .local-Namens verwenden.

Download-Seite: Im Browser (Adressleiste, ohne https) http://<Server-IP>/ca öffnen. Die Seite lädt pos-root-ca.crt herunter und zeigt den SHA-256-Fingerabdruck; vergleichen Sie ihn mit der Ausgabe des Installationsskripts, bevor Sie das Zertifikat installieren. Die Seite gibt es nur auf Port 80; alles andere dort wird auf HTTPS umgeleitet. Alternativ kopieren Sie pos-root-ca.crt per USB-Stick, Netzwerkfreigabe oder E-Mail auf jedes Gerät. Installieren Sie es dort einmalig als vertrauenswürdig – auf jedem Gerät – und vergleichen Sie dabei den Fingerabdruck (siehe unten):

  • Linux-Kasse: sudo cp pos-root-ca.crt /usr/local/share/ca-certificates/ && sudo update-ca-certificates. Danach die Kassen-App neu starten.
  • Android: Einstellungen › Sicherheit › Verschlüsselung und Anmeldedaten › Zertifikat installieren › CA-Zertifikat. Unter Android 12–15 (Pixel): Sicherheit & Datenschutz › Weitere Sicherheitseinstellungen › Verschlüsselung und Anmeldedaten › …. Bei Samsung und anderen Herstellern weicht der Weg ab – alternativ in den Einstellungen nach „CA-Zertifikat“ suchen. Der anschließende Hinweis „Netzwerk wird möglicherweise überwacht“ ist normal. Danach die Kassen-App neu starten.
  • Browser für den Web-Admin: Firefox (und Chrome unter Linux) im Browser importieren – in Firefox unter Einstellungen › Datenschutz & Sicherheit › Zertifikate anzeigen › Zertifizierungsstellen › Importieren.

Fingerabdruck prüfen (muss mit der Ausgabe des Installationsskripts übereinstimmen): openssl x509 -in pos-root-ca.crt -noout -fingerprint -sha256 (nur den Teil nach = vergleichen). Unter Android wird der SHA-256-Fingerabdruck nach dem Import in den Zertifikatsdetails angezeigt (Vertrauenswürdige Anmeldedaten › Nutzer), sofern das Gerät ihn anzeigt.

Kassen ohne Zertifikat-Installation (Prüfcode)

Android- und Linux-Kassen müssen das Stammzertifikat nicht von Hand installieren. Beim Koppeln prüfen sie es selbst: Im Back Office (Terminals › Kopplungscode erzeugen) zeigt der Kopplungsdialog neben dem QR-Code einen Zertifikat-Prüfcode (z. B. K7QF-3MXA-9TD2-P8WC-4HNB-6R).

  • Mit Kamera: den QR-Code scannen. Er enthält Serveradresse, Kopplungscode und Prüfcode; die Kasse lädt das Stammzertifikat vom Server, vergleicht es mit dem Prüfcode und koppelt erst danach.
  • Ohne Kamera: die https://-Adresse eintragen und im Kopplungsbildschirm Kopplungscode und Prüfcode eintippen. Der Prüfcode ist unabhängig von Groß-/Kleinschreibung und Bindestrichen.

Eine neu eingerichtete Kasse, die dem Zertifikat noch nicht vertraut, meldet nicht „Server nicht erreichbar“, sondern zeigt nach Eingabe der https://-Adresse direkt den Kopplungsbildschirm – dort Kopplungscode und Prüfcode eingeben (oder den QR-Code scannen). Ist der Server wirklich nicht erreichbar, bleibt es bei der Meldung „Server nicht erreichbar“.

Passt das heruntergeladene Zertifikat nicht zum Prüfcode, bricht die Kasse ab und sendet den Kopplungscode nicht. Der Prüfcode erscheint nur, wenn der Server hinter Caddy mit lokaler Zertifizierungsstelle läuft (Datei /etc/pos-caddy/pos-root-ca.crt vorhanden); ohne ihn koppelt die Kasse wie bisher und verlangt, dass das Zertifikat auf dem Gerät installiert ist. Erzeugt der Server eine neue Zertifizierungsstelle (z. B. nach Löschen von /var/lib/pos-caddy), müssen die Kassen mit dem neuen Prüfcode neu gekoppelt werden. Browser (Web-Admin, Browser-Kasse) sind davon nicht betroffen – sie brauchen weiterhin das installierte Zertifikat.

Feste IP-Adresse und richtige Uhrzeit. Die Zertifikate enthalten nur die IP-Adressen, die der Server bei der Installation hatte. Geben Sie ihm eine feste IP-Adresse oder eine DHCP-Reservierung (im Router fest zugewiesene Adresse). Ändert sich die IP-Adresse des Servers, führen Sie das Installationsskript erneut aus. Das Stammzertifikat bleibt dabei gleich – die Geräte müssen es nicht neu installieren. Kassen, die bereits die alte IP-Adresse gespeichert haben, zeigen danach „Server nicht erreichbar“ und lassen sich an der Kasse derzeit nicht umstellen – geben Sie dem Server in diesem Fall seine bisherige IP-Adresse zurück (z. B. per DHCP-Reservierung) und führen Sie das Skript erneut aus. Richten Sie neue Kassen deshalb möglichst mit einem lokalen Namen statt der IP-Adresse ein. Außerdem sind diese Zertifikate nur wenige Stunden gültig und werden laufend automatisch erneuert – Geräte mit falsch gehender Uhr lehnen sie ab. Lassen Sie die Uhrzeit auf allen Geräten automatisch stellen.
Das Installationsskript prüft die Systemuhr und warnt (ohne abzubrechen), wenn sie nicht mit einem Zeitserver abgeglichen ist oder vor dem Erstellungsdatum des Pakets liegt. Zertifikate, die auf einer falschen Uhr erstellt wurden, lehnen Geräte mit richtiger Uhr ab. Stellen Sie die Zeit zuerst richtig (sudo timedatectl set-ntp true) und führen Sie das Skript erneut aus. Wurde die Zertifizierungsstelle schon mit falscher Uhr erzeugt, löschen Sie /var/lib/pos-caddy und starten Sie das Skript neu; alle Kassen müssen dann mit dem neuen Prüfcode neu gekoppelt werden.

Lokaler Name (optional)

Zusätzlich kann das Zertifikat lokale Namen enthalten, z. B. kasse.fritz.box. Die Kassen verwenden dann https://kasse.fritz.box statt einer IP-Adresse. Die Adresse an der Kasse enthält keinen Port. Haben Sie im Einrichtungsassistenten einen anderen Port gewählt, geben Sie ihn dem Skript wie oben beschrieben zusätzlich mit, z. B. sudo ./install-service.sh /opt/pos-server 8090 --local-name kasse.fritz.box.

Den Schalter für jeden Namen wiederholen:

sudo ./install-service.sh --local-name kasse.fritz.box --local-name pos.lan
  • Gespeichert: Das Skript merkt sich die Namen (Ablageort siehe Tabelle unten). Ein erneuter Aufruf ohne --local-name behält sie bei. Ein Aufruf mit dem Schalter ersetzt die gespeicherte Liste vollständig – geben Sie also alle Namen an, die erhalten bleiben sollen. --clear-local-names entfernt alle Namen und lässt sich nicht mit --local-name kombinieren.
  • Erlaubte Namen: einfache Rechnernamen aus Buchstaben (a–z, ohne Umlaute), Ziffern, Bindestrichen und Punkten, z. B. kasse.fritz.box oder pos.lan – ohne https://, Port oder Pfad. Höchstens 253 Zeichen, jeder Teil zwischen zwei Punkten höchstens 63 Zeichen und ohne Bindestrich am Anfang oder Ende. Großbuchstaben werden in Kleinbuchstaben umgewandelt. IP-Adressen und localhost lehnt das Skript ab; sie stehen ohnehin im Zertifikat. Namen müssen mindestens einen Punkt enthalten (z. B. kasse.fritz.box, nicht kasse) – einteilige Namen kann die Kassen-App über HTTPS nicht verwenden. Namen auf .local werden abgelehnt: Diese löst der Router nicht auf; <Rechnername>.local nimmt das Skript ohnehin auf. Enthält die gespeicherte Datei einen ungültigen Eintrag (z. B. nach einer Bearbeitung von Hand), bricht ein erneuter Aufruf ab, bis Sie die Datei korrigieren oder die Namen mit dem Schalter neu setzen.
  • Der Router muss den Namen kennen: Das Skript trägt den Namen nur in das Zertifikat ein. Der DNS-Server des Routers (oder eines lokalen DNS-Servers) muss jeden Namen in die IP-Adresse des Servers auflösen. Beispiel FRITZ!Box: Sie löst für Geräte in ihrem Heimnetz den Namen <Gerätename>.fritz.box auf – maßgeblich ist der Name, der unter Heimnetz › Netzwerk angezeigt wird (dort lässt er sich auch ändern). Wird der Server dort als kasse angezeigt, verwenden Sie kasse.fritz.box. Am zuverlässigsten ist das, wenn der Server seine Adresse per DHCP von der FRITZ!Box bezieht (mit fester Zuweisung, siehe oben). Andere Router verwenden eine andere Endung oder erwarten einen Eintrag von Hand. Prüfen können Sie das an einem PC im Ladennetz mit nslookup kasse.fritz.box – die Antwort muss die IP-Adresse des Servers enthalten. Android-Geräte, bei denen Privates DNS auf einen festen Anbieter eingestellt ist, lösen lokale Namen nicht auf – stellen Sie dort Automatisch oder Aus ein oder verwenden Sie die IP-Adresse.
  • Vorteil: Das Zertifikat für den Namen hängt nicht von der IP-Adresse ab. Ändert sich die IP-Adresse des Servers, arbeiten Kassen, die den Namen verwenden, weiter, sobald der Router den Namen auf die neue Adresse auflöst – ohne erneuten Aufruf des Skripts. Für Geräte, die die IP-Adresse verwenden (z. B. den Browser am Admin-PC), führen Sie es trotzdem erneut aus. Den Namen selbst sollten Sie danach nicht mehr ändern (auch nicht den Gerätenamen im Router oder den Rechnernamen des Servers): Kassen mit dem alten Namen lassen sich an der Kasse derzeit nicht umstellen.

Wenn eine neue Version Probleme macht

Startet die neue Version nicht sauber, holt der Server nach drei fehlgeschlagenen Starts in Folge von selbst das vorherige Programm zurück (die fehlerhafte Datei wird als pos-server.jar.failed-… aufbewahrt). Sie müssen dazu nichts tun.

Diesen Rückfall-Wächter richtet unter Linux das Skript install-service.sh ein. Wurde die Installation vor Version 1.1.0 eingerichtet, fehlt er, bis das Skript einmal erneut ausgeführt wurde – siehe Kapitel 16 – Nach dem Update auf v1.1.0.

Ein Zurückholen des Programms macht keine Datenänderungen rückgängig. Bringt eine neue Version die Datenbank auf einen neuen Stand und geht danach etwas schief, läuft zwar wieder das alte Programm – aber auf der bereits veränderten Datenbank. Bitte betrachten Sie das Zurückholen deshalb nicht als vollständige Umkehr. Genau dafür wird vor jeder Installation die Datenbanksicherung angelegt: sie ist der einzige Weg zurück auf den Stand von vorher. Der Server notiert dabei in einer Datei im Installationsverzeichnis, welche Sicherung zu diesem Versuch gehört, damit im Ernstfall nicht danach gesucht werden muss. Rufen Sie in einem solchen Fall Ihren Betreuer an, bevor Sie weiterarbeiten.

Nach einer Rücksicherung auf einem anderen Rechner

Wenn Sie eine Sicherung auf einem anderen Rechner einspielen – nach einem Hardwaretausch etwa –, meldet die Seite, dass das gespeicherte Zugangstoken nicht mehr gelesen werden kann. Tragen Sie das Token dort einmal neu ein, dann ist wieder alles in Ordnung.

Das ist Absicht, kein Fehler. Der Schlüssel zum Entschlüsseln des Tokens liegt auf dem Rechner selbst und nicht in der Datensicherung. Würde das Token eine Sicherung überdauern, könnte jeder, der eine Kopie Ihrer Datensicherung in die Finger bekommt, damit auf die internen Programmversionen zugreifen. Der kleine Aufwand einer Neueingabe ist der Preis dafür – und er fällt genau einmal an.
Wenn sich gar kein Token speichern lässt. Meldet die Seite, auf diesem Server sei kein Update-Schlüssel eingerichtet, dann fehlt dem Rechner der Schlüssel UPDATE_TOKEN_KEY, mit dem das Token überhaupt erst versiegelt werden kann. Das betrifft ältere Installationen, die vor Version 1.1.0 eingerichtet wurden. Der interne Kanal bleibt so lange gesperrt – das ist Absicht, denn ein Token im Klartext abzulegen wäre schlechter als gar keines.

Abhilfe: Ihr Betreuer führt auf dem Server einmal install-service.sh erneut aus. Das Skript legt den Schlüssel an, falls er fehlt, und lässt einen vorhandenen unverändert – ein bereits gespeichertes Token überlebt die Neuinstallation also. Den Schlüssel niemals von Hand neu erzeugen – sonst lässt sich das gespeicherte Token nicht mehr lesen. Danach lässt sich das Token wie oben beschrieben eintragen. Der öffentliche Kanal funktioniert die ganze Zeit über normal weiter, denn er braucht kein Token.

Server zuerst, dann die Geräte

Aktualisieren Sie immer zuerst den Server und danach Kassen, Bestellstationen und den Web-Admin. Der Web-Admin wird vom Server selbst ausgeliefert und ist nach dem Neustart automatisch auf demselben Stand. Ein neuerer Web-Admin gegen einen älteren Server fällt still auf die alten Rollenregeln zurück und sieht dabei aus, als funktioniere alles.

Android-Kassen aktualisieren

Android-Kassen holen ihre App direkt von Ihrem Server – ohne Internetzugang am Gerät und ohne Token. Der Server legt die Android-App der Version, die er selbst installiert, beim Herunterladen im Ordner update-client/ neben dem Server ab, nachdem er sie gegen die veröffentlichte Prüfsumme geprüft hat. Dieser Ordner bleibt bei Server-Aktualisierungen erhalten.

  1. Lassen Sie den Server die neue Version laden: durch die nächtliche Prüfung oder mit Herunterladen auf dieser Seite.
  2. Auf dem Anmeldebildschirm der Kasse erscheint – nur wenn sich die App selbst geändert hat – der Hinweis App-Update verfügbar. Mit Nach Updates suchen können Sie jederzeit selbst nachsehen.
  3. Wählen Sie Herunterladen und installieren. Die Kasse lädt die App herunter, prüft sie erneut und übergibt sie an Android.
  4. Android fragt selbst nach der Bestätigung der Installation. Diese Abfrage lässt sich nicht umgehen. Beim ersten Mal müssen Sie außerdem erlauben, dass die App Updates installieren darf.
Warum erscheint nicht bei jeder Server-Version ein Hinweis? Die Kasse vergleicht nur die interne Versionsnummer der App (versionCode), nicht die Versionsbezeichnung. Eine Server-Version mit kleiner Korrektur, bei der die App unverändert bleibt, löst deshalb keine Nachfrage aus – die Kasse kann dann eine ältere Versionsbezeichnung anzeigen als der Server, ohne dass etwas fehlt.

Ein Server, der nicht über diese Seite aktualisiert wurde, hat keine App zum Verteilen; die Kassen melden dann einfach, dass kein Update vorliegt. Schlägt die Prüfung der heruntergeladenen Datei fehl oder wird die Installation abgebrochen, bleibt die installierte App unverändert.

Problem melden (GitHub-Meldungen aus dem Backoffice)

Im Backoffice (Admin-Oberfläche) gibt es im Benutzermenü den Eintrag Problem melden. Er legt aus dem Backoffice heraus eine Meldung (ein Issue) im GitHub-Repository an, das Ihr Administrator dafür festgelegt hat. Sie müssen dazu kein GitHub-Konto besitzen: Der Server sendet die Meldung mit einem hinterlegten Zugangstoken. Die Kassenoberflächen (Kasse, Bestellstation) bieten diese Funktion derzeit nicht.

Einrichtung (Administrator)

  1. Serverschlüssel: Auf dem Server muss UPDATE_TOKEN_KEY in der Umgebungsdatei hinterlegt sein (derselbe Schlüssel, der auch das Aktualisierungs-Token versiegelt). Fehlt er, weist die Einstellungsseite darauf hin und das Token kann nicht gespeichert werden. Nach dem Eintragen den Server neu starten.
  2. Token erzeugen: Legen Sie bei GitHub ein fein granuliertes persönliches Zugriffstoken (Fine-grained personal access token) an, beschränkt auf genau das eine Ziel-Repository und mit ausschließlich der Berechtigung Issues: Lesen & Schreiben (Issues: Read and write). Keine weiteren Berechtigungen, keine weiteren Repositories.
  3. Eintragen: Unter Einstellungen → Problemmeldungen den Repository-Inhaber und den Repository-Namen eintragen, mit Einstellungen speichern sichern, dann das Token im Feld Neues Token einfügen und Token speichern wählen. Inhaber und Name werden nur auf gültige Schreibweise geprüft, nicht gegen GitHub.

Alternative: Update-Token verwenden

Statt eines eigenen Tokens können Sie – typischerweise auf einer privaten Installation, die ihre Aktualisierungen ohnehin mit einem Zugangstoken bezieht (Kanal und Zugangstoken) – unter Einstellungen → Problemmeldungen den Schalter Update-Token für Meldungen verwenden einschalten und mit Einstellungen speichern sichern. Das ist eine bewusste Entscheidung des Administrators; ohne sie wird nie auf das Update-Token ausgewichen.

  • Voraussetzung: Unter Einstellungen → Aktualisierungen ist ein lesbares Update-Token hinterlegt. Fehlt es oder ist es auf diesem Server nicht lesbar, ist der Schalter gesperrt und die Seite nennt den Grund.
  • Berechtigung: Das Update-Token braucht dann zusätzlich Issues: Lesen & Schreiben (Issues: Read and write) auf dem Ziel-Repository der Meldungen. Fehlt diese Berechtigung, weist GitHub die Meldung ab und der Dialog meldet ein abgelehntes Token. Beachten Sie: Ein Token deckt dann das Installieren von Aktualisierungen und das Anlegen von Meldungen ab.
  • Host-Regel: Das Update-Token wird nur an den Host gesendet, für den die Aktualisierung eingerichtet ist. Die GitHub-API-Adresse der Problemmeldungen muss deshalb mit der API-Adresse der Aktualisierungsquelle übereinstimmen (ein abschließender Schrägstrich und Groß-/Kleinschreibung des Hosts spielen keine Rolle). Sonst wird das Speichern abgewiesen; der Grund steht dann direkt über Einstellungen speichern (siehe Fehlermeldungen). Wird die Aktualisierungsquelle später auf einen anderen Host umgestellt, sendet der Server keine Meldung mehr, bis die Einstellungen der Problemmeldungen erneut passend gespeichert sind.
  • Das eigene Token bleibt unberührt: Ein bereits hinterlegtes eigenes Token wird beim Einschalten weder gelöscht noch verwendet; das Eingabefeld dafür ist gesperrt, solange der Schalter an ist. Nach dem Ausschalten wird wieder das eigene Token verwendet. Ein- oder Ausschalten löscht auch das Update-Token nie.
So wird das Token behandelt:
  • Es ist nur schreibbar: Nach dem Speichern zeigt die Seite nur eine maskierte Kennung (Token hinterlegt) und den Speicherzeitpunkt, nie das Token selbst. Zum Ersetzen einfach ein neues eintragen, zum Löschen Token entfernen.
  • Der Server speichert es verschlüsselt. Es taucht in keiner Antwort und in keinem Log auf.
  • Der verschlüsselte Wert ist Teil der Datenbanksicherungen, auf einem Rechner ohne denselben UPDATE_TOKEN_KEY aber nicht lesbar. Nach einer Wiederherstellung auf einem anderen Rechner meldet die Seite Ein Token ist hinterlegt, kann auf diesem Server aber nicht gelesen werden – tragen Sie das Token dann erneut ein.
  • Wenn Sie die GitHub-API-Adresse auf einen anderen Host ändern, wird das gespeicherte eigene Token gleichzeitig gelöscht (das Update-Token nie), damit es nie an einen fremden Host gesendet wird. Danach das Token neu eintragen.

Privates oder öffentliches Repository

Der Schalter Repository ist öffentlich ist Ihre Erklärung. Standardmäßig folgt er dem Aktualisierungskanal (Kanal und Zugangstoken): beim öffentlichen Kanal öffentlich, beim internen Kanal privat. Der Server prüft bei GitHub nicht nach, ob das stimmt. Stellen Sie den Schalter deshalb nur auf privat, wenn das Repository wirklich privat ist.

Titel und Beschreibung sind Ihr Text und Ihre Verantwortung. Bei einem öffentlichen Repository kann sie jeder lesen. Geben Sie dort keine Kunden-, Beleg-, Mitarbeiter- oder sonstigen personenbezogenen Daten ein, keine Passwörter und keine Zugangsdaten.

Was automatisch angehängt wird – und was nie

  • Automatisch: App- und Server-Version, Plattform, meldende Oberfläche (Backoffice), aktuelle Ansicht (bereinigt und auf 100 Zeichen gekürzt), Zeitpunkt, Rolle des Meldenden und – nur bei einem privaten Repository – der Name des Betriebs.
  • Nie: Belege, Rechnungen, Kundendaten, Mitarbeiterdaten, Tokens oder Zugangsdaten. Diese Daten werden nicht gelesen und nicht angehängt.

Optionaler Log-Auszug

Auszug aus dem Server-Log anhängen (bereinigt) ist standardmäßig aus. Wenn Sie ihn einschalten, hängt der Server nur WARN-/ERROR-Zeilen der letzten Logs, höchstens 50 Zeilen an; gewöhnliche INFO-Zeilen (etwa Anmeldeversuche mit Benutzernamen) werden nicht übernommen. Enthält das Log keine solche Zeile, fehlt der Log-Block in der Vorschau einfach. Auch eine Fehlermeldung kann Namen oder Kennungen von Mitarbeitern enthalten. Bekannte Muster (Tokens, Zugangsdaten, E-Mail-Adressen und ähnliches) werden zuvor entfernt, das ist aber nur ein Bestmühen und keine Garantie. Die eigentliche Absicherung ist die Vorschau:

  1. Mit Vorschau zeigt der Dialog unter Genau dieser Text wird veröffentlicht den vollständigen Text samt Ziel-Repository.
  2. Mit Meldung senden wird genau dieser Text veröffentlicht, unverändert: Der Server hält die Vorschau zwischen und sendet sie, er baut sie nicht neu. Wurde ein Log-Auszug gewählt, ist das Senden ohne vorherige Vorschau nicht möglich. Die Schaltfläche Meldung senden wird erst rund 1,5 Sekunden nach dem Erscheinen der Vorschau aktiv, damit ein Doppelklick auf Vorschau nicht ungelesen sendet. Schlägt das Senden fehl, erscheint der Hinweis oben im Dialog; Ihr Text bleibt erhalten.
  3. Eine Vorschau verfällt nach 15 Minuten, nach einmaligem Senden, bei einer Änderung des Ziels in den Einstellungen und bei jedem Neustart des Servers.

Lesen Sie den Auszug in der Vorschau durch und verzichten Sie im Zweifel auf ihn. Bei einer Meldung ohne Log-Auszug kann der Text auch ohne Vorschau gesendet werden.

Grenzen

  • Titel: höchstens 200 Zeichen; Beschreibung: höchstens 10 000 Zeichen.
  • Höchstens 5 Meldungen pro Stunde und Installation (nicht pro Person). Auch fehlgeschlagene Sendeversuche zählen, denn GitHub kann die Meldung trotz Fehlermeldung angelegt haben. Eine Ablehnung schon vor dem Senden (z. B. fehlendes Pflichtfeld) kostet nichts.
  • Erwähnungen mit „@“ in Ihren Texten werden entschärft, damit GitHub niemanden benachrichtigt.

Protokollierung

Jede gesendete Meldung wird als Vorgang CREATE_ISSUE_REPORT im Prüfprotokoll festgehalten: wer sie gesendet hat und die Issue-Nummer. Titel und Beschreibung werden nie ins Protokoll geschrieben. Siehe Protokollierte Operationen.
