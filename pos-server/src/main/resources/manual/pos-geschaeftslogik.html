1.4 Zentrale Entwurfsmuster

  • Fehler als PosException: Services signalisieren erwartete Fehler per throw PosException(PosErrorCode, HttpStatusCode, …); der Server antwortet einheitlich im Format RFC 7807 (ProblemDetail mit code und traceId). Das alte Result<T, DataError>-Muster ist in den Server-Features abgelöst und lebt nur noch in einigen Randmodulen.
  • dbQuery-Transaktionen: Services steuern die Transaktionsgrenzen via dbQuery {}. Repositories haben keine eigenen Transaktionen.
  • Service-Repository-Trennung: Repositories liefern Entities, Services liefern DTOs.
  • Zwei Phasen bei fiskalischen Vorgängen: Phase 1 schreibt Bestellung/Rechnung in einer Datenbanktransaktion (REPEATABLE_READ, bei Konflikt wiederholt), Phase 2 signiert nach dem Commit mit der TSE. Die Signierprüfung (Terminal, TSE-Modus) läuft vor Phase 1, damit ein abgelehnter Vorgang nichts schreibt.
  • Geld exakt dezimal: Beträge sind BigDecimal in der Datenbank (DECIMAL(19,4)) und Strings auf der Leitung — nie Double. Die Clients rechnen mit dem :platform-money-Modul und zeigen z. B. 16,90 € an.

2.3 VatMappingUtil.determineVat()

Dateipfad: ecr/data/.../utils/config/VatMappingUtil.kt

Pfand: Pfand- und Pfandrückgabe-Positionen bestimmen ihre Klasse nicht über den Produkttyp, sondern über den PfandType des Produkts (determineDepositVat, Warenumschließung nach Anhang C); ohne PfandType fällt sie mit Warnung auf Klasse A zurück.

Algorithmus (Priorität absteigend):

1. Konfiguration aus ShopConfigurationManager laden
2. VatRules für productType ermitteln
3. Prioritätslogik:
   ├─ isToGo == true  UND  toGo != null  →  toGo-Klasse verwenden
   ├─ isReduced == true  UND  reduced != null  →  reduced-Klasse verwenden
   └─ Sonst  →  default-Klasse verwenden
4. Vat-Entity per findById(vatClass) laden

2.4 Fallback-Logik

Bei fehlender oder ungültiger Konfiguration greift die hardcodierte Zuordnung:

ProdukttypDine-InToGo / ReducedKlasse → Steuersatz
FOODA → 19%B → 7%Speisen
DRINKSA → 19%A → 19%Getränke
RETAILA → 19%A → 19%Einzelhandel
SERVICEA → 19%A → 19%Dienstleistungen
VOUCHERC → 0%C → 0%Gutscheine
OTHERSC → 0%C → 0%Sonstige

2.5 Besonderheit FOOD

Speisen haben als einziger Produkttyp drei verschiedene MwSt-Szenarien:

FOOD + Dine-In          →  Klasse A  →  19%
FOOD + ToGo             →  Klasse B  →   7%
FOOD + Reduced (Senior) →  Klasse B  →   7%

3.3 Preisberechnung im Detail

Eingabe:
  unitPrice   = Produktpreis oder benutzerdefinierter Preis
  extrasPrice = Σ(extras.price) für alle Extras dieses Items
  discount    = Multiplikator (1.0 = 0%, 0.9 = 10% Rabatt, 0.5 = 50% Rabatt)

Formel:
  finalPrice = (unitPrice + extrasPrice) × discount     (2 Stellen, HALF_UP)

Rechenbeispiel:
  Burger:      unitPrice = 12,00€
  Extra Käse:  extrasPrice = 1,50€
  Rabatt:      discount = 0.90 (10% Rabatt)

  finalPrice = (12,00 + 1,50) × 0.90 = 13,50 × 0.90 = 12,15€

3.4 Wichtig: Eine Zeile pro Mengeneinheit

Wenn ein Kunde 3× Burger bestellt, werden 3 separate OrderItem-Zeilen in der Datenbank erstellt — nicht eine Zeile mit quantity = 3. Jede Zeile hat ihren eigenen unitPrice, finalPrice und vat-Wert.

Beispiel: 3× Burger á 12,00€

t_order_item:
  ID=101  product=Burger  unitPrice=12,00  finalPrice=12,00  itemStatus=OPEN
  ID=102  product=Burger  unitPrice=12,00  finalPrice=12,00  itemStatus=OPEN
  ID=103  product=Burger  unitPrice=12,00  finalPrice=12,00  itemStatus=OPEN

4.2 Rechnungsnummern: Monatszähler bill_number_sequence

Dateipfad: server/.../bill/data/repository/BillRepositoryImpl.kt (generatedBillNumber), Tabelle bill_number_sequence (V82)

Format: RE-YYMMDD-N (z.B. RE-260506-39); N zählt je Monat ab 0.

1. Zeile des Monats (period = 'YYMM') lesen: SELECT … FOR UPDATE
   └─ fehlt sie: anlegen (INSERT … ON CONFLICT DO NOTHING), Startwert = höchstes
      bereits vergebenes N des Monats + 1, sonst 0
2. N = next_value, dann next_value = N + 1  — in der Transaktion des Belegs
3. Commit: Nummer und Beleg sind gemeinsam gespeichert
   Rollback: auch der Zähler wird zurückgesetzt → keine Lücke

Die Zeilensperre serialisiert parallele Belege prozessübergreifend. Unter REPEATABLE_READ erhält eine wartende Transaktion nach dem Commit der anderen einen Serialisierungsfehler (40001) und wird mit frischem Snapshot wiederholt (BillWriteConflict.retrying, RetryConfig.AGGRESSIVE). Bleibt nach allen Wiederholungen ein Konflikt, antwortet der Server mit 409 BILL_NUMBER_COLLISION, nie mit 500 – ebenso für eine Unique-Verletzung auf bill_number.

Warum: Früher war N ein count(*) der Belege des Monats. Zwei parallele Transaktionen zählten dieselben Zeilen, und die In-Process-Reservierung (BillNumberTracker) wurde vor dem Commit freigegeben: fünf parallele Belege einer Kasse ergaben im Praxistest vier Belege und einen 500er mit doppelter RE-260506-39. Der BillNumberTracker bleibt als zweite Sicherung; eine Nummer wird nur einmal gezogen (jede Ziehung erhöht den Zähler), eine abgelehnte Reservierung bricht die Transaktion ab.

Bestellnummern: derselbe Zähler-Mechanismus

Dateipfad: server/.../order/data/repository/OrderRepositoryImpl.kt (create), Tabelle order_number_sequence (V82)

Format: ORD-YYYYMMDD-N (z.B. ORD-20261008-7); N ist ein durchlaufender Zähler (eine Zeile, prefix = 'ORD'), nicht je Tag zurückgesetzt. Die Zeile wird mit SELECT … FOR UPDATE gesperrt und in der Transaktion der Bestellung erhöht; beim ersten Mal wird sie angelegt, Startwert = höchstes bereits vergebenes N bzw. höchste Bestell-ID + 1. Bei Rollback der Bestellung wird auch der Zähler zurückgesetzt. Ein Serialisierungsfehler (40001) einer wartenden Bestellung wird von createOrder mit withRetryThrows wiederholt; der TSE-Schritt läuft erst nach dem Commit.

Warum: Früher war N die höchste Bestell-ID + 1, in der Bestell-Transaktion gelesen. Zwei Kellner, die im selben Moment bestellten, zogen dieselbe Nummer, und der Verlierer endete mit 500 (t_order_order_number_unique); der In-Process-OrderNumberTracker gab die Reservierung vor dem Commit frei und ist entfallen.

4.3 BillServiceImpl.createBillInternal() — Schritt für Schritt

Dateipfad: server/.../bill/data/service/BillServiceImpl.kt

Transaktionsisolation: TRANSACTION_REPEATABLE_READ (Phase 1, bei Konflikt wiederholt)

Schritt 1: Rechnungsnummer generieren & reservieren
  billNumber = generateAndReserveBillNumber()   → z.B. "RE-250219-3" (Monatszähler, Abschnitt 4.2)

Schritt 2: Bill-Entity erstellen
  Bill.new {
    employeeId, tableSession, billNumber
    billAmount = billAmount           (Summe der Item-Preise, ohne Trinkgeld)
    tips = tips                       (Trinkgeldbetrag)
    startTime = session.startTime
    endTime = currentTimeStamp()

Schritt 3: OrderItems validieren & assoziieren
  Für jedes orderItem-ID im Request:
    ├─ Item in der Session finden (throw bei Fehler)
    ├─ Status prüfen: itemStatus MUSS OPEN sein
    ├─ item.bill = bill
    └─ item.itemStatus = PAID

Schritt 4: Zahlungen erstellen
  Für jede PaymentRequest:
    ├─ PaymentType per ID laden
    └─ Payment.new {

       }

    mehr als eine Aktion und eine davon nicht kombinierbar ⇒ 409 PROMOTION_NOT_COMBINABLE

    Largest-Remainder-Verfahren (PromotionApportionment, cent-genau)

  Validierung: Σ(payments.amount) == billAmount − promotionAmount + tips
    (sonst PAYMENT_TOTAL_MISMATCH)

Schritt 5: Gutschein-Einlösung (optional)
  Für jede VoucherRedeemRequest:
    ├─ Gutschein per Nummer laden (nur INTERNAL-Quelle)
    ├─ VoucherRedeem-Entity erstellen
    ├─ voucher.remainingValue aktualisieren
    └─ Wenn Restbetrag == 0: voucher.fullyRedeemedAt setzen

Schritt 6: MwSt-Aufschlüsselung (BillVatDetail)
  ├─ Items nach MwSt-Rate gruppieren:
  │    vatToTotalPrice = items.groupBy { it.vat }
  │                           .mapValues { Σ(finalPrice) }
  │
  ├─ tipRecipient == OWNER (TrinkgeldAG, steuerbar): Trinkgeld verteilen
  │    Gewichte (OwnerTipWeights): Brutto nach Aktionen, ersatzweise Brutto
  │    vor Aktionen, ersatzweise Positionsanzahl
  │    Aufteilung per Largest-Remainder auf 2 Stellen (Summe == tips exakt,
  │    identisch zum DSFinV-K-Export)
  │      total = gruppenTotal + Trinkgeldanteil
  │      → createBillVat(bill, total, vat)
  │    Sonderfall: Rechnung ohne Positionen → eine 0%-Zeile „Nicht steuerbar“
  │
  └─ tipRecipient == EMPLOYEE (TrinkgeldAN): Trinkgeld NICHT in MwSt-Gruppen
       Für jede MwSt-Gruppe:
         → createBillVat(bill, gruppenTotal, vat)
       Das Trinkgeld erhält KEINE eigene BillVatDetail-Zeile (nicht steuerbar,
       kein Umsatz); es geht über ProcessDataBuilder.nonTaxableExtra in den
       5. Brutto-Slot ("nicht steuerbar") der TSE-Signatur ein.

Schritt 7: Finalisierung
  bill.paidAmount = Σ(payments.amount)
  bill.endTime = currentTimeStamp()

Schritt 8: MwSt-Validierung
  vatSum = Σ(bill.vatDetails.totalAmount)
  ├─ OWNER:     vatSum == paidAmount
  └─ EMPLOYEE:  vatSum == paidAmount − tips   (Trinkgeld nicht steuerbar)
  paidAmount = billAmount − promotionAmount + tips
  Bei Abweichung → Validierungsfehler, die Rechnung wird nicht angelegt

  processData = ProcessDataBuilder.build(KASSENBELEG_V1, bonType, vatDetails, payments)
  clientId = terminalRepository.findByDeviceId(deviceId)
  tseService.signTransaction(...)
    ├─ Erfolg → tseSigningStatus = SIGNED
    └─ Fehler:
       ├─ FAIL-Modus  → Exception → Rollback
       └─ QUEUE-Modus → tseSigningStatus = QUEUED, in Queue einreihen

  Wenn keine OPEN-Items mehr in Session:
    ├─ tableSessionRepository.completeSession(...)
    └─ NotificationService.notifyTableStatusUpdate(...)

Sperrung & Schutz vor abgeschlossenen Sessions: createBill sperrt die Session-Zeile per FOR UPDATE und lehnt eine bereits abgeschlossene Session mit 409 SESSION_ALREADY_CLOSED ab — ebenso die Bestellerstellung und der Storno von Positionen. Damit kann keine neue Bestellung an eine soeben abgerechnete Session angehängt werden.

Invariante: Ein Tisch darf niemals eine abgeschlossene Session (completed = true) als currentSession referenzieren. Durchgesetzt zentral in TableSession.end() (setzt completed und räumt den Tisch-Zeiger, sobald der Tisch noch auf diese Session zeigt). Bereits beschädigte Datensätze repariert der Admin-Endpunkt POST /api/tables/repair-completed-sessions: offene Positionen werden auf eine frische Session verschoben, sonst wird der verwaiste Zeiger gelöscht.

4.4 Thekenverkauf ohne Tischzuordnung (Gutschein)

Der frühere Quick-Sale-Flow wurde entfernt. Er war der einzige Nutzer der zweistufigen TSE-API (StartTransaction … FinishTransaction) und damit der einzige Weg, auf dem ein Vorgang nach Transaktionsbeginn abgebrochen werden konnte — der Fall AVBelegabbruch nach DSFinV-K Anhang B S. 46, für den der DSFinV-K-Export keinen Produzenten besitzt.

Der verbliebene Anwendungsfall ohne Tischzuordnung ist der Gutscheinverkauf an der Theke (VoucherService.createVoucher mit sessionId = null):

1. Session auf dem virtuellen VOUCHER-Tisch öffnen
2. Gutschein-Position direkt an die Session hängen (ohne Order-Entity, orders_id = null)
3. Bill erstellen via BillService.createBill(...)
   → signiert atomar per quickSign (Start + Finish in einem WormAPI-Aufruf)
   → es kann keine Transaktion offen bleiben

Die fiskalische Form ist unverändert: genau ein Kassenbeleg-V1-Vorgang, keine zusätzliche AVBestellung.

5. MwSt-Berechnung auf Rechnungen (BillVatDetail)

5.1 Formel: createBillVat()

Dateipfad: server/.../bill/data/service/BillServiceImpl.kt

Eingabe:
  totalAmount = Bruttobetrag der MwSt-Gruppe (inklusive anteiliges Trinkgeld bei OWNER)
  vat.vatRate  = z.B. 0.19 (für 19%)

Berechnung:
  vatRate_multiplier = vat.vatRate + 1.0        z.B. 1.19
  netAmount          = totalAmount ÷ vatRate_multiplier   (Scale 2, HALF_UP)
  vatAmount          = totalAmount − netAmount

Ergebnis:
  BillVatDetail { bill, vat, totalAmount, netAmount, vatAmount }

5.2 MwSt-Gruppenverteilung bei Inhaber-Trinkgeld (OWNER)

Wenn bill.tipRecipient == OWNER (abgerechnet von ADMIN):
  1. Items nach MwSt-Rate gruppieren:
     Gruppe A (19%): gruppenTotal_A = Σ(finalPrice) der A-Items
     Gruppe B (7%):  gruppenTotal_B = Σ(finalPrice) der B-Items

  2. Gesamtsumme:
     sumAlleGruppen = gruppenTotal_A + gruppenTotal_B

  3. Anteile per Largest-Remainder (PromotionApportionment.apportion):
     jeden Idealanteil tips × gruppenTotal ÷ sumAlleGruppen auf Cent abrunden,
     verbleibende Cents nacheinander an die größten Rundungsreste
     → Σ(Anteile) == tips exakt

  4. Trinkgeld verteilen:
     total_A = gruppenTotal_A + anteil_A
     total_B = gruppenTotal_B + anteil_B

  5. createBillVat() für jede Gruppe aufrufen

5.3 Rechenbeispiel

Gegeben:
  Item A1: finalPrice = 80,00€, MwSt-Klasse A (19%)
  Item A2: finalPrice = 20,00€, MwSt-Klasse A (19%)
  Item B1: finalPrice = 50,00€, MwSt-Klasse B (7%)
  Tips = 10,00€
  Employee = ADMIN (tipRecipient = OWNER)

Schritt 1 — Gruppierung:
  Gruppe A: 80,00 + 20,00 = 100,00€
  Gruppe B: 50,00€
  Gesamt:   150,00€

Schritt 2 — Trinkgeldverteilung (OWNER, Largest-Remainder):
  Idealanteile: A = 6,6667  B = 3,3333   → abgerundet 6,66 + 3,33 = 9,99
  Rest 0,01 an den größten Rundungsrest (A: 0,0067)  →  A = 6,67  B = 3,33

  total_A = 100,00 + 6,67 = 106,67€
  total_B =  50,00 + 3,33 =  53,33€

Schritt 3 — MwSt-Berechnung (createBillVat):
  Gruppe A (19%):
    vatRate_multiplier = 1,19
    netAmount  = 106,67 ÷ 1,19 = 89,64€    (Scale 2, HALF_UP)
    vatAmount  = 106,67 − 89,64 = 17,03€

  Gruppe B (7%):
    vatRate_multiplier = 1,07
    netAmount  = 53,33 ÷ 1,07 = 49,84€     (Scale 2, HALF_UP)
    vatAmount  = 53,33 − 49,84 = 3,49€

Validierung (OWNER):
  Σ(vatDetails.totalAmount) = 106,67 + 53,33 = 160,00€
  paidAmount                = 150,00 + 10,00      = 160,00€  ✓
Gleiches Beispiel mit Mitarbeiter-Trinkgeld (EMPLOYEE, Nicht-ADMIN):

  Gruppe A: total = 100,00€ (ohne Trinkgeld)
    netAmount = 100,00 ÷ 1,19 = 84,03€
    vatAmount = 100,00 − 84,03 = 15,97€

  Gruppe B: total = 50,00€ (ohne Trinkgeld)
    netAmount = 50,00 ÷ 1,07 = 46,73€
    vatAmount = 50,00 − 46,73 = 3,27€

Validierung (EMPLOYEE):
  Σ(vatDetails.totalAmount) = 100,00 + 50,00 = 150,00€
  billAmount                = 150,00€  ✓
  (Tips = 10,00€ separat, NICHT in MwSt-Gruppen — nicht steuerbar,
   keine eigene BillVatDetail-Zeile)

6.1 Neun-Schritt atomarer Prozess

Dateipfad: server/.../bill/data/service/BillServiceImpl.kt

Transaktionsisolation: TRANSACTION_REPEATABLE_READ (Phase 1, bei Konflikt wiederholt)

Schritt 1: Entities finden

  ├─ Bill per billId laden
  └─ TableSession per bill.tableSession laden

Schritt 2: Validierung — DREI Guards, jeder antwortet mit HTTP 409
  ├─ (a) Bill darf nicht bereits storniert sein und selbst kein Storno-Beleg sein:
  │      bill.deletingReason == null UND bill.deletedBill == null
  ├─ (b) Der Geschäftstag darf nicht abgeschlossen sein (Runde 3, KABS-1):
  │      kein Z-Bon für den Tag der Rechnung
  │      Grund: nach dem Abschluss sind die Daten in einem exportierten
  │      Kassenabschluss eingefroren. Ein Storno würde reversedByBill auf den
  │      Einlösungen des Originals setzen (und damit die businesscases des
  │      geschlossenen Abschlusses rückwirkend verändern), und die
  │      Bargeldrückgabe erreichte den aktuellen Abschluss nie.
  └─ (c) Für die Rechnung darf keine ausgestellte Ausgangsrechnung existieren
         (SALES_INVOICE_IMMUTABLE): erst die Ausgangsrechnung per Gutschrift
         (Typ 381) stornieren. Gilt ebenso für den Zahlartwechsel.

Berechtigung: Storno erfordert die Fähigkeit BILL_VOID
  (DELETE /api/v1/bills/{id}; vorgegeben ab Filialleitung), der Zahlartwechsel
  BILL_CHANGE_PAYMENT (vorgegeben ab Kasse). Beide können per Manager-PIN
  für genau diesen Vorgang geliehen werden (ElevationScope.TILL_OVERRIDES).

Schritt 3: Storno-Rechnung erstellen (negierte Beträge)

  }

Schritt 4: Zahlungen als REFUNDED markieren

    payment.paymentStatus = REFUNDED
    payment.refundTime    = currentTimeStamp()
    payment.refundedBillId = reverseBill

Schritt 5: MwSt-Details umkehren
  Für jedes BillVatDetail der Originalrechnung:

      bill        = reverseBill
      totalAmount = original.totalAmount.negate()
      netAmount   = original.netAmount.negate()
      vatAmount   = original.vatAmount.negate()
      vat         = original.vat
    }

Schritt 6: Gutscheine rückgängig machen
  Für jede VoucherRedeem der Originalrechnung:
    redeemVoucher(reverseBill, negierter Betrag)
    → Erhöht voucher.remainingValue wieder

Schritt 7: TSE-Signierung
  bonType = AV_TRAINING (Training) oder AV_BELEGSTORNO (Normal)

  → Signierung mit FAIL- oder QUEUE-Modus

Schritt 8: Session wiederöffnen (falls nötig)
  Wenn session.completed == true:
    session.completed = false
    session.endTime   = null
    table.tableStatus = OCCUPIED
    table.currentSession = session

Schritt 9: Neue OPEN-Items erstellen

      order      = null    ← Kein Link zur Original-Order (TSE-Signatur bewahren)
      session    = original.session
      bill       = null    ← Nicht abgerechnet
      itemStatus = OPEN    ← Kann erneut abgerechnet werden
      ... (alle anderen Felder kopiert)
    }

6.2 Zahlartwechsel = Storno + Neubuchung

Endpunkt: POST /api/v1/bills/{id}/rebook (Befugnis BILL_CHANGE_PAYMENT, Prüfprotokoll REBOOK_BILL). Eine Transaktion (REPEATABLE_READ, bei Konflikt wiederholt):

Schritt 1: Prüfen (alles vor dem ersten Schreibzugriff)
  ├─ Handelnder darf abrechnen (kein Bestellstations-Konto)
  ├─ Bill ist ein bestehender Verkauf; kein Gutscheinverkauf, kein
  │   Forderungsausgleich (409 BILL_REBOOK_UNSUPPORTED)
  ├─ Storno-Guards (a)–(c) wie oben
  └─ Neue Zahlung: Σ payments == billAmount − promotionAmount + tips,
      und Zahlung, Gutscheine oder Trinkgeld weichen ab (409 BILL_REBOOK_NO_CHANGE)
      Trinkgeld kleiner als bisher nur mit BILL_VOID
      (403 BILL_REBOOK_TIP_DECREASE_FORBIDDEN)

Schritt 2: Rechnungsentwurf zum Beleg verwerfen (ausgestellte Rechnung → Guard (c))

Schritt 3: Storno wie in 6.1, mit stornoReason = ZAHLARTWECHSEL,
  alle Positionen dupliziert, Session wird NICHT wieder geöffnet

Schritt 4: Neubuchung über den normalen Abrechnungsweg
  ├─ Positionen = die Duplikate aus Schritt 3
  ├─ employee     = ursprünglicher Bediener

  ├─ Zahlungen, Gutschein-Einlösungen und gesamtes Trinkgeld aus der Anfrage
  ├─ Aktionen des Originals, bewertet zum Zeitpunkt des Originals;
  │   anderer Abzug als beim Verkauf → 409 BILL_REBOOK_PROMOTION_CHANGED
  └─ rebooksBill = Original

Schritt 5 (nach dem Commit): TSE-Signierung, Storno zuerst, dann Neubuchung
  (jeweils signiert oder in die Warteschlange, je nach TSE-Modus)

Tisch und Sitzung bleiben unberührt. Die Antwort ist die Neubuchung.

  (refundedBillId == null) und werden nicht zusätzlich negiert.

  1. Barzahlungen (EUR zuerst, dann alphabetisch nach Währung)
  2. Unbare Zahlungen (EUR zuerst, dann alphabetisch nach Währung)

Schritt 8: Kassenbuch-Eintrag erstellen
  Typ: CASH_SALE

  Einzelposten (LineItems):
    ├─ (+) MwSt-Einnahmen: eine Zeile pro MwSt-Rate
    │       vorzBetrag = "+{brutto}", ustSatz = "19" / "7" / ...
    │       belegtext = "Einnahme MwSt. 19%"
    │
    └─ (-) Unbare Zahlungen: eine Zeile pro unbarer Zahlungsart
            vorzBetrag = "-{betrag}"
            belegtext = "Unbare Zahlung: CARD"

  TSE-Signierung: keine. Das Z-Bon-Aggregat wird nicht mehr signiert
    (Status NOT_APPLICABLE, keine TSE-Transaktion; AEAO zu § 146a
    Nr. 1.11.2). Signiert werden nur die Bargeldbewegungen des Abschlusses
    (Kassendifferenz, Trinkgeld-Auszahlungen, Aufstockung, täglicher
    Geldtransit), siehe 10.7. Ein Abschluss ohne solche Bewegungen signiert nichts.

Schritt 9: Saldo-Berechnung (nur Kassenbücher der Kasse; ein Tresor hat seinen
          eigenen Kassensturz)
  openingBalance  = vorheriger Z-Bon.closingBalance   (oder 0,00 wenn erster)
  Kassenbuch-Einträge nach Eintragstyp einsortiert (zBonBucket), nur bei
  typneutralen Einträgen nach Vorzeichen:
    EXPENSE  → expenses      (z.B. Barausgabe; auch die Storno-Seite einer
                              korrigierten Barausgabe)
    REVENUE  → cashRevenue
    NEUTRAL  → transfers     (Geldtransit, Kassendifferenz … — weder
                              Einnahme noch Ausgabe)
  closingBalance  = openingBalance + expenses + cashRevenue + transfers

  report.openingBalance  = openingBalance
  report.expenses        = expenses
  report.cashRevenue     = cashRevenue
  report.closingBalance  = closingBalance
  report.endTime         = currentTimeStamp()

Schritt 10: Kassenbuch-Einträge sperren
  Alle Kassenbuch-Header im Zeitraum:
    header.isLocked = true
    header.zBon = report (wenn noch nicht zugeordnet)

  Validierung: Keine ungesperrten Einträge mehr vorhanden

Schritt 11: Sessions zuordnen
  Alle abgeschlossenen, nicht-Training-Sessions ohne Z-Bon:
    session.zBon = report

9.4 Nummerierung

Der Datenbank-PK (zbon_id) ist eine BIGSERIAL-Sequenz und kann Lücken haben. Maßgeblich ist die gedruckte Z-Nummer zbon_nummer: Sie wird als max(zbon_nummer) + 1 in der Abschluss-Transaktion berechnet und ist damit aufsteigend und lückenlos. 10.3 Saldo-Berechnung

Dateipfad: server/.../kassenbuch/data/repository/KassenbuchRepositoryImpl.kt

Eingabe:
  lastBalance    = current_balance des vorherigen Headers (oder 0 bei erstem Eintrag)
  lineItemsData  = Liste der Einzelposten mit vorzBetrag
  entryType      = KassenbuchEntryType (mit isIncoming)

Berechnung:
  1. totalAmount = Σ(parseBigDecimal(lineItem.vorzBetrag))

  2. Saldo des Headers:
     Einnahme (isIncoming = true):  currentBalance = lastBalance + |totalAmount|
     Ausgabe  (isIncoming = false): currentBalance = lastBalance − |totalAmount|

  3. Sub-Saldo je Einzelposten (laufend):
     runningBalance = lastBalance
     Für jede Zeile:
       lineAmount = parseBigDecimal(lineItem.vorzBetrag)
       Einnahme: runningBalance += |lineAmount|
       Ausgabe:  runningBalance −= |lineAmount|
       lineItem.subBalance = runningBalance

Rechenbeispiel:
  lastBalance = 500,00€
  Einnahme: CASH_SALE (isIncoming = true)
  Zeile 1: vorzBetrag = "+71,50" (19% MwSt)
  Zeile 2: vorzBetrag = "+28,50" (7% MwSt)

  totalAmount = 71,50 + 28,50 = 100,00€
  currentBalance = 500,00 + 100,00 = 600,00€

  Zeile 1: subBalance = 500,00 + 71,50 = 571,50€
  Zeile 2: subBalance = 571,50 + 28,50 = 600,00€

10.4 belegNr-Generierung

Algorithmus (KassenbuchRepositoryImpl.nextBelegNrBlocking):
  1. Präfix = JJJJ-MM des aktuellen Monats
  2. MAX(belegNr) mit diesem Präfix im selben Kassenbuch ermitteln
  3. Nächste Nummer = laufende Nummer + 1 (vierstellig), sonst 0001
     → z.B. "2026-09-0024"

→ Monatlicher Reset: Jeden Monat beginnt die Nummerierung bei 0001
→ Zählung je Kassenbuch (Kasse und Tresor getrennt)
→ Storno eines Eintrags: belegNr "STORNO-<Original>"

10.5 vorzBetrag-Formatierung

Eingabe: "100.50" oder "100,50" (beide akzeptiert)

Verarbeitung:
  1. Punkt durch Komma ersetzen: "100,50"
  2. Vorzeichen prüfen:
     Bereits mit +/−? → unverändert
     Sonst:
       isIncoming = true  → "+100,50"
       isIncoming = false → "−100,50"

Ausgabe: "+100,50" oder "−100,50" (Komma als Dezimaltrennzeichen)

10.6 DATEV-Export

Das frühere 13-Spalten-CSV (KassenbuchCsvExporter) gibt es nicht mehr. Kassenbuch-Daten gehen heute über:

  • DATEV-Kassenbuch-XML (DatevXmlExportServiceImpl) — siehe DATEV XML Export; nicht von der Kontenzuordnung abhängig.
  • DATEV-Buchungsstapel (EXTF, mit und ohne Belege; DatevBuchungsstapelExportServiceImpl) — verlangt die DATEV-Kontenzuordnung und antwortet ohne sie mit 409. 10.7 TSE-Integration

Jeder Kassenbuch-Eintrag wird TSE-signiert. Der processType folgt dem BON_TYP des Eintragstyps (KassenbuchDsfinvkMapping.getBonTyp) — er ist nicht pauschal SonstigerVorgang:

BON_TYP „Beleg“ (alle Eintragstypen außer CLOSING_BALANCE)
  processType = PROCESS_TYPE_RECEIPT ("Kassenbeleg-V1")
  processData = Beleg^<5 USt-Buckets>^<Zahlungen>   (siehe 8.1)
                Buckets kind-bewusst: NON_CASH_PAYMENT-Zeilen sind
                Zahlart, kein Umsatz, und erscheinen nur als Unbar.
  → Privateinlage, Geldtransit, Barausgabe usw. (TSER-2;
    Anhang I S. 119/120)

BON_TYP „AVSonstige“ (nur CLOSING_BALANCE)
  processType = PROCESS_TYPE_OTHER ("SonstigerVorgang")
  processData = Serialisierte Eintragsdaten (Freitext)
  → Legacy: neue CLOSING_BALANCE-Einträge werden vom Service
    abgelehnt (KABS-3) — ein Zählprotokoll gehört in den
    Kassensturz/DifferenzSollIst.

Gemeinsam:
  referenceId = belegNr
  clientId    = Terminal-Identifier per deviceId
                (Tagesabschluss: TSE-Client der für die Ladenkasse bestimmten
                 Kasse, sonst der aufrufenden Kasse)

Das Z-Bon-Tagesabschluss-Aggregat ist die Ausnahme von dieser Regel: es ist zwar formal ein CASH_SALE-Eintrag (BON_TYP „Beleg“), wird aber nicht mehr TSE-signiert (Status NOT_APPLICABLE, keine TSE-Transaktion; AEAO zu § 146a Nr. 1.11.2). (Historie: vom 05.08.2026 bis 09.10.2026 signierte es bewusst als SonstigerVorgang.) Signiert bleiben die Bargeldbewegungen des Abschlusses — Kassendifferenz, Trinkgeld-Auszahlungen, Aufstockung und täglicher Geldtransit — unter dem TSE-Client der für die Ladenkasse bestimmten Kasse, sonst der aufrufenden Kasse; ein Abschluss ohne solche Bewegungen signiert nichts. Es wird vom DSFinV-K-Export vollständig ausgeschlossen (is_zbon_aggregate), weil es nur Buchhaltung über bereits exportierte Bons ist — als Kassenbeleg signiert hätte es den Tagesumsatz, den die TSE bereits belegweise signiert hat, im TAR ein zweites Mal deklariert. Details siehe manual/tse-dokumentation.html, Nachtrag 05.08.2026.

11. Gutscheine (Voucher)

11.1 Einlösung bei Rechnungserstellung

In BillServiceImpl.createBillInternal() werden Gutscheine wie folgt eingelöst:

Für jede VoucherRedeemRequest:
  1. Gutschein per voucherNumber laden (nur INTERNAL-Quelle)
  2. VoucherRedeem-Entity erstellen:
     ├─ bill = aktuelle Rechnung
     ├─ voucher = geladener Gutschein
     └─ redeemAmount = eingelöster Betrag
  3. Gutschein-Saldo aktualisieren:
     remainingAmount = voucher.remainingValue − redeemAmount
     ├─ remainingAmount <= 0:
     │    voucher.remainingValue = 0
     │    voucher.fullyRedeemedAt = currentTimeStamp()
     └─ remainingAmount > 0:
          voucher.remainingValue = remainingAmount

11.2 Training-Modus

Im Training-Modus wird der Gutschein-Saldo NICHT verändert. Training-Rechnungen sind nicht fiskalisch relevant.

11.3 Storno-Rückgängigmachung

Bei Rechnungsstorno wird die Gutscheineinlösung rückgängig gemacht:

Für jede VoucherRedeem der Originalrechnung:
  redeemVoucher(reverseBill, negierter Betrag)
  → voucher.remainingValue wird wieder erhöht

11.4 Z-Bon-Integration

Während der Z-Bon-Erstellung werden alle Gutschein-Erstellungen und -Einlösungen des Zeitraums dem Z-Bon zugeordnet:

Voucher.find { zBonId == null AND startTime < createdAt < endTime }
  → voucher.zBon = report

VoucherRedeem.find { zBonId == null AND reversedByBill == null
                     AND startTime < redeemedAt < endTime }
  → voucherRedeem.zBon = report
  (eine durch Storno umgekehrte Einlösung wird nie einem Abschluss zugeordnet)
