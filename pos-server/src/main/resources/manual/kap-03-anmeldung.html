Kapitel 03 – Anmeldung & Sicherheit

Voraussetzung: gekoppeltes Gerät

Eine Kasse kann erst benutzt werden, wenn sie mit dem Server gekoppelt ist. Beim Start prüft die App, ob der Server erreichbar, eingerichtet und das Gerät gekoppelt ist. Ein nicht gekoppeltes Gerät zeigt statt der Anmeldung den Bildschirm Gerät koppeln: Dort geben Sie den Kopplungscode ein, den jemand mit dem Recht zur Terminalverwaltung im Web-Admin unter Geräte → Terminals erzeugt, oder scannen (Android) den QR-Code. Wie ein Gerät erstmals verbunden wird, beschreibt Kapitel 02.

Nach dem Update auf Version 1.1 müssen bestehende Kassen gekoppelt werden. Ein Gerät ohne Kopplung wird beim Anmelden auf den Kopplungsbildschirm geleitet. Stellen Sie vor dem Update sicher, dass jemand im Web-Admin Kopplungscodes erzeugen kann (Fähigkeit TERMINAL_MANAGE). Nach fünf falschen oder abgelaufenen Codes von derselben Netzwerkadresse lehnt der Server Kopplungsversuche von dort für bis zu fünf Minuten ab.

Wurde der Code mit beim Koppeln an der TSE registrieren erzeugt, registriert der Server das Terminal beim Koppeln an der TSE. Gelingt das nicht, bleibt das Gerät ungekoppelt und meldet, dass es nicht an der TSE registriert werden konnte; wenden Sie sich an einen Administrator, der die TSE prüft und bei Bedarf einen neuen Code erzeugt. Ein solcher Code verfällt außerdem, sobald die TSE-Admin-Sitzung endet, in der er erzeugt wurde („Kopplungscode abgelaufen“).

Die Server-Adresse lässt sich im Anmeldebildschirm nicht mehr ändern. Solange das Gerät nicht gekoppelt ist, wird sie auf dem Startbildschirm (wenn der Server nicht erreichbar ist), auf dem Kopplungsbildschirm über Server ändern oder über den QR-Code eingestellt. Ein gekoppeltes Gerät bleibt bei dem Server, mit dem es gekoppelt wurde.

Browser-Station koppeln

Eine Kasse oder Bestellstation lässt sich auch im Browser betreiben (/pos/). Voraussetzung ist, dass die Rolle im Web-Admin unter Einstellungen → Browser-Stationen aktiviert ist (siehe Kapitel 13); solange keine Rolle aktiviert ist, antwortet /pos/ mit „nicht gefunden“ (404).

  1. Im Web-Admin unter Geräte → Terminals einen Kopplungscode für das Terminal erzeugen – wie bei jedem Gerät. Neben dem Code zeigt der Web-Admin den Link für den Browser (<Adresse>/pos/?code=<Code>).
  2. Im Browser des Geräts http://<Server-Adresse>:8080/pos/ öffnen, oder den Link aufrufen – dann ist der Code bereits eingetragen.
  3. Auf dem Bildschirm Gerät koppeln den Code eingeben (falls nicht per Link ausgefüllt) und bestätigen. Danach läuft die Station in ihrer Rolle (Kasse oder Bestellstation) wie auf einem Tablet.

Das Gerät bleibt im Browserprofil gekoppelt. Nach 10 Minuten ohne Eingabe wird die angemeldete Person abgemeldet; das Gerät bleibt gekoppelt und zeigt wieder die Anmeldung. Ein zweiter Tab im selben Browserprofil startet keine zweite Station, sondern zeigt den Hinweis „Diese Station ist bereits in einem anderen Tab geöffnet“. Für mehrere Stationen auf einem Rechner verwenden Sie getrennte Browserprofile.

Weitere Einzelheiten, Einschränkungen und Sicherheitshinweise stehen in Kapitel 13 – Browser-Stationen.

Anmeldung

Der Anmeldebildschirm hat ein einziges Formular für beide Anmeldearten. Bei erfolgreicher Authentifizierung wird ein JWT-Token-Paar erstellt (Zugangstoken und Aktualisierungstoken).

  1. Geben Sie im Feld Benutzername oder Mitarbeiternummer Ihren Benutzernamen oder Ihre Mitarbeiternummer ein.
  2. Geben Sie im Feld Passwort oder PIN Ihr Passwort bzw. Ihre PIN ein.
  3. Optional: Anmeldedaten merken anhaken.
  4. Tippen Sie auf Anmelden.

Oben im Bildschirm zeigt eine Statusanzeige, ob der Server erreichbar ist (Online/Offline; antippen prüft erneut); daneben lässt sich die Sprache wählen.

Zugangsdaten merken an der Kasse: Ist „Angemeldet bleiben" aktiviert, füllt die Kasse Benutzername und Passwort bei der nächsten Anmeldung vor. Passwort, Geräte-Token sowie Zugangs- und Aktualisierungstoken speichert die Kasse verschlüsselt. Den Schlüssel verwahrt auf Android der geschützte Schlüsselspeicher des Geräts (Android Keystore), am PC der Schlüsselbund des Betriebssystems; gibt es dort keinen nutzbaren Schlüsselbund, liegt er in einer Datei, die nur der angemeldete Benutzer lesen kann. Eine kopierte Datenbankdatei allein ist daher nicht lesbar. Auf Android gelangen die Daten der Kasse weder in Gerätesicherungen noch bei einem Geräteumzug auf ein neues Gerät. Nutzt ein PC die Schlüsseldatei, enthält eine Sicherung des gesamten Benutzerverzeichnisses auch den Schlüssel. Gegen ein gerootetes Gerät oder Schadsoftware unter demselben Benutzerkonto schützt die Verschlüsselung nicht. Wer vor der Kasse steht, kann sich mit dem gemerkten Passwort anmelden – an gemeinsam genutzten Kassen die Option daher nicht aktivieren. Siehe auch Kasse verlangt erneut die Kopplung oder die Anmeldung.

Token-Verwaltung

  • Zugangstoken (kurzlebig) – Wird für API-Aufrufe verwendet.
  • Aktualisierungstoken (langlebig) – Ermöglicht die automatische Verlängerung der Sitzung. Kassen speichern es auf dem Gerät. Der Web-Admin erhält es ausschließlich als HttpOnly-Cookie, das kein Skript im Browser lesen kann; sein Zugangstoken liegt nur im Arbeitsspeicher der Seite und wird nach dem Neuladen über das Cookie erneuert.
  • Mehrere Tabs – Erneuern zwei Tabs gleichzeitig ihre Sitzung, akzeptiert der Server das eben ersetzte Token noch 10 Sekunden lang, statt alle Sitzungen des Mitarbeiters zu beenden.
  • Geräte-ID – Wird als X-Device-ID-Header für die Gerätezuordnung übertragen.
  • Kopplungstoken – Wird bei der Kopplung ausgestellt, auf dem Gerät gespeichert und bei jeder Anfrage als X-Device-Token-Header mitgesendet. Es gilt nur für den Server, mit dem das Gerät gekoppelt wurde.
  • Sitzungsende – Läuft die Sitzung eines Mitarbeiters ab oder wird sie widerrufen, kehrt die Kasse zur Anmeldung zurück; die Kopplung bleibt erhalten. Ist der Server nur vorübergehend nicht erreichbar (z. B. während eines Neustarts), bleibt die Sitzung bestehen.
  • Validierung – GET /api/auth/validate für leichtgewichtige Token-Prüfung.

Trainingsmodus

Der Trainingsmodus ermöglicht das Üben ohne fiskalische Auswirkungen. Er ist eine Eigenschaft des Mitarbeiterkontos, nicht der Anmeldung: Wer mit einem Trainingskonto angemeldet ist, arbeitet im Trainingsmodus.

  • Aktivierung: Im Web-Admin unter Betrieb → Personal beim Mitarbeiter den Schalter Schulungsmodus einschalten (siehe Kapitel 10). Einen Schalter auf dem Anmeldebildschirm gibt es nicht. Umschalten darf nur, wer Mitarbeiter bearbeiten darf (Berechtigung EMPLOYEE_WRITE, standardmäßig Manager und Admin) – auch am eigenen Konto: Ein Kassierer kann sich nicht selbst in den Trainingsmodus versetzen (der Server antwortet mit 403, der Schalter ist ohne die Berechtigung gesperrt).
  • Erkennung: Tische mit Trainingsvorgängen tragen im Tischplan die Kennzeichnung Training.
  • TSE: Trainings-Transaktionen werden mit dem Typ Training signiert.
  • Beleg: Ein Trainingsbeleg trägt am Kopf und am Fuß die Kennzeichnung TRAININGSBELEG / *** KEIN VERKAUF - SCHULUNGSBELEG *** – auf dem Bondrucker, im PDF, beim Nachdruck und auch auf dem Storno eines Trainingsbelegs. So kann er nicht mit einem echten Kassenbeleg verwechselt werden.
  • Belegliste: In den Belegen eines Z-Bons (Kasse und Web-Admin) stehen Trainingsbelege mit, gekennzeichnet mit Training; in Umsatz und Summen zählen sie nicht.
  • Berichte: Trainingsberichte sind separat einsehbar.

Temporäre Manager-Sitzung (Manager-PIN)

Fehlt einem Kassierer für einen Vorgang die nötige Fähigkeit, kann ein Manager sie ihm mit seiner PIN vorübergehend leihen. Der Kassierer bleibt dabei angemeldet und behält alles, was er ohnehin darf; er erhält zusätzlich nur die angefragte Fähigkeit – beim allgemeinen Freigabedialog aus dem Menü die kleine Gruppe der Kassen-Freigaben: Zahlart ändern, Beleg stornieren, Rabatt gewähren, Position stornieren, Preis überschreiben und Tischsitzung übernehmen. Die Sitzung übernimmt nicht mehr die Identität des Managers.

EigenschaftBeschreibung
Dauer3 Minuten (180 Sekunden); wird bei Navigation bzw. bei einem berechtigten Vorgang kurz vor Ablauf verlängert. Eine Verlängerung setzt das Ende auf „jetzt + 3 Minuten“, nie weiter; eine abgelaufene Sitzung lässt sich nicht verlängern, dafür ist die Manager-PIN erneut nötig
Höchstdauer15 Minuten ab Eingabe der Manager-PIN – eine feste Obergrenze, die keine Verlängerung überschreitet, auch wenn an der Kasse ständig navigiert wird. Danach endet die Freigabe; die Kasse zeigt Manager-Freigabe abgelaufen, und der Manager muss die PIN erneut eingeben. Der Server lehnt eine Verlängerung nach Erreichen der Obergrenze mit HTTP 409 (AUTH_STEP_UP_CAP_REACHED) ab.
BindungGilt nur auf dem anfragenden Gerät und nur für den anfragenden Mitarbeiter – ein zweiter Kassierer an derselben Kasse erbt sie nicht
UmfangNur Kassen-Freigaben; alles andere (z. B. Tagesabschluss, Konfiguration) lehnt der Server ab. Verliehen wird nur, was der Manager selbst besitzt.
FreigebendeNur Mitarbeiter, deren Gruppe die Fähigkeit ELEVATION_APPROVE enthält (vorgegeben: MANAGER, ADMIN)
Server-SynchronisationAlle 30 Sekunden

Ablauf:

  1. Mitarbeiter fordert die Freigabe an.
  2. Manager gibt Benutzername (oder Mitarbeiternummer) und PIN ein.
  3. Die Fähigkeit ist auf diesem Gerät für diesen Mitarbeiter freigeschaltet.
  4. Automatisches Ende nach Ablauf der Zeit, spätestens 15 Minuten nach der PIN-Eingabe – oder sofort über Sitzung beenden. Der Server entzieht die geliehene Fähigkeit dann mit der nächsten Anfrage, nicht erst bei Ablauf.

Verlängern und Beenden darf nur der Mitarbeiter, dem die Fähigkeit geliehen wurde; ein Kollege an derselben Kasse erhält HTTP 403.

Aktionen während einer temporären Sitzung werden im Prüfprotokoll dem Kassierer zugeschrieben, der sie ausgeführt hat; der freigebende Manager wird dazu vermerkt.

Bestellstation (Betrieb ohne Anmeldung)

Ein Terminal mit der Rolle Bestellstation (siehe Terminalverwaltung) ist ein fester Bestellpunkt an Theke oder Bar – typischerweise für Aushilfen, die kein eigenes Mitarbeiterkonto haben. Die Station kennt keinen Anmeldebildschirm: einmal gekoppelt, zeigt sie beim Einschalten sofort die Kassenoberfläche in reduzierter Form.

MöglichNicht möglich
Bestellungen auf Tische aufnehmen und an die Küche senden; freie Tische öffnen (nur mit Reihum-Mitarbeiterzuweisung); bestehende Bestellungen einsehen; Reservierungen anlegen und ändern; Kunden zuordnen; Benachrichtigungen Abrechnen (auch teilweise), Rechnung anfordern, Rechnung oder Beleg drucken, Rechnung teilen, Tisch umbuchen, Zahlart ändern, Beleg stornieren; Rabatt gewähren oder individuellen Preis setzen (auch nicht mit Manager-PIN); Abhol- und virtuelle Tische öffnen; Reservierungen löschen; Berichte, Finanzdokumente, Einstellungen, Mein Profil

Das Menü der Station umfasst genau Dashboard (Tische), Reservierungen und Benachrichtigungen (auf dem Telefon über das Glockensymbol oben im Dashboard). Abgerechnet wird an der Kasse durch einen Mitarbeiter.

Tische öffnen. Einen freien Tisch öffnet die Station nur, wenn die Reihum-Mitarbeiterzuweisung eingeschaltet ist. Der Tisch gehört dann dem Mitarbeiter, den die Rotation als Nächsten bestimmt – nicht der Station. Dieser Mitarbeiter rechnet den Tisch an der Kasse ab. Ist die Reihum-Mitarbeiterzuweisung ausgeschaltet, meldet die Station, dass sie freie Tische nur mit eingeschalteter Reihum-Mitarbeiterzuweisung öffnet, und verweist an die Kasse. Ist der Rotationspool leer, meldet sie stattdessen, dass kein Mitarbeiter im Rotationspool ist, und verweist auf das Hinzufügen von Mitarbeitern unter Reihum-Mitarbeiterzuweisung. Abhol- und virtuelle Tische (z. B. Gutschein) öffnet die Station nie. Auf Tische mit einer bereits offenen Sitzung – auch Abholungen – bucht sie jederzeit Bestellungen; der zuständige Mitarbeiter bleibt dabei unverändert.

Keine Abrechnung. Die Station rechnet in keiner Form ab. Im Tischfenster (Antippen und Halten eines besetzten Tisches) fehlen Rechnung und Rechnung anfordern immer – unabhängig davon, wem der Tisch gehört, und auch dann, wenn die Einstellung Mitarbeiterübergreifende Abrechnung eingeschaltet ist. Der Kellner rechnet unter seiner eigenen Anmeldung ab. Maßgeblich ist, unter wem abgerechnet wird, nicht das Gerät: Der Server lehnt das Abrechnen (ganz, teilweise oder mit Karte), die Rechnungsanforderung, den Zahlartwechsel (Storno und Neubuchung) und den Belegstorno unter dem gemeinsamen Stationskonto mit HTTP 403 ab – für die Station selbst und auch während einer temporären Manager-Sitzung, denn die Freigabe leiht dem Stationskonto nur Rechte, die Buchung bliebe dem Stationskonto zugeordnet. Meldet sich dagegen ein Mitarbeiter, etwa ein Manager, mit seinem eigenen Konto am Gerät der Bestellstation an, darf er dort abrechnen: Der Beleg wird ihm zugeordnet (Bediener im DSFinV-K-Export) und über den TSE-Client des Stationsgeräts signiert.

Keine Preisänderungen. Im Fenster Artikel bearbeiten bietet die Station weder das Feld Rabatt noch den Schalter Individueller Preis an; jede Position wird zum Listenpreis gebucht. Preise und Nachlässe legt ein angemeldeter Mitarbeiter fest. Auch der Server lehnt eine Bestellung unter dem gemeinsamen Stationskonto mit Rabatt (DISCOUNT_NOT_ALLOWED) oder individuellem Preis (CUSTOM_PRICE_NOT_ALLOWED) mit HTTP 403 ab – unabhängig von der Höhe des Rabatts und auch während einer temporären Manager-Sitzung. Die Regel gilt für die Person, unter der die Bestellung gebucht wird, nicht für das Gerät: Ein Manager, der sich mit seinem eigenen Konto am Gerät der Bestellstation anmeldet, bucht Rabatt und individuellen Preis wie an der Kasse – die Bestellung wird ihm zugeordnet und über den TSE-Client des Stationsgeräts signiert. Am Kassen-Terminal bleiben Rabatt und individueller Preis wie gewohnt möglich.

Alle an einer Station ohne Anmeldung aufgenommenen Bestellungen werden dem gemeinsamen Geräte-Mitarbeiterkonto und der jeweiligen Station zugeschrieben; die Station signiert ihre Bestellungen über ihren eigenen TSE-Client. Was später abgerechnet wird, trägt den Namen des abrechnenden Mitarbeiters. Einen Trainingsmodus gibt es an der Station nicht – ohne Anmeldebildschirm gibt es auch keine Auswahl dafür.

Korrekturen nach dem Senden brauchen einen Manager – vor Ort. Eine bereits an die Küche gesendete Position kann an der Station nur storniert werden, während ein Manager an der Station angemeldet ist. Die Station kann keine Storno-Freigabe anfordern: Das Symbol Stornieren fehlt in der Auswahlleiste, solange kein Manager angemeldet ist, und auch der Server lehnt eine Storno-Anfrage des Stationskontos mit HTTP 403 (STATION_STORNO_REQUIRES_MANAGER) ab – es wird nichts vorgemerkt, das unbeantwortet verfallen könnte.

Manager-Anmeldung an der Station. Über die Schaltfläche Manager anmelden (Schloss-Symbol in der Seitenleiste) gibt ein Manager seine Mitarbeiternummer (oder seinen Benutzernamen) und seine PIN ein; daraus wird eine temporäre Manager-Sitzung an diesem Gerät. An der Station schaltet sie genau zwei Dinge frei: Stornieren gesendeter Positionen und das Umsetzen von Positionen oder Tischen. Abrechnen, Rabatte und individuelle Preise bleiben auch dann gesperrt. Storno und Umsetzung werden dem Manager zugeordnet (der Storno-Dialog nennt ihn: Freigabe durch …) – im Storno- bzw. Umsetzungsdatensatz, im Prüfprotokoll (Autorisierungsart TEMPORARY_SESSION, freigebender Manager; das gilt auch für das Umsetzen eines ganzen Tisches) –, nicht dem gemeinsamen Stationskonto. Die TSE-Transaktion eines Stornos nennt nur den TSE-Client der Station, keinen Mitarbeiter. Endet die Sitzung (Schaltfläche Beenden oder Ablauf), hat die Station wieder nur ihre eigenen Rechte, und ein Storno wird erneut abgelehnt. Läuft die Sitzung von selbst ab (3 Minuten ohne Aktivität, Höchstdauer erreicht oder vom Server beendet), erscheint an Kasse und Station die Warnung Manager-Freigabe abgelaufen; wer Beenden drückt oder sich abmeldet, bekommt keine Meldung.

Öffnet ein Umsetzen unter der Manager-Anmeldung einen freien Tisch, gehört der neue Tisch nicht dem Manager, sondern dem Mitarbeiter, den die Rotation bestimmt (der Manager nur, wenn er im Rotations-Pool ist und an der Reihe).

Das Umsetzen von Positionen bleibt ohne Manager-Anmeldung als offene Genehmigung möglich (siehe unten); diese Umsetzung wird dem Stationskonto zugeordnet, mit dem genehmigenden Manager im Prüfprotokoll.

Wo offene Genehmigungen landen. Vorgemerkte Anfragen sammelt der Web-Admin auf dem Startbildschirm in der Karte Autorisierungs-Anfragen samt Anzahl. Jeder Eintrag nennt den angefragten Vorgang, die Mitarbeiternummer des Anfragenden, die Kennung des Terminals, von dem die Anfrage stammt (z. B. TER-001 – nicht der frei vergebene Terminalname), und den Zeitpunkt; dazu die Aktionen Genehmigen und Ablehnen, letztere mit Pflichtangabe eines Grundes. Eine bereits wartende Anfrage ist damit genauso zuzuordnen wie eine, die während der Anzeige eintrifft. Lässt sich ein Mitarbeiter oder ein Terminal nicht mehr auflösen – etwa nach dem Löschen –, steht an dieser Stelle die technische ID, damit die Anfrage sichtbar bleibt. Beantwortet niemand eine Anfrage innerhalb von drei Minuten, verfällt sie, und das anfragende Gerät meldet „Genehmigungsanfrage abgelaufen“. Ein Neustart des Servers verwirft offene Anfragen.

Widerruf und Deaktivierung. Ist das Gerät mit dem Server verbunden, meldet der Server einen Widerruf oder eine Deaktivierung sofort: Das Gerät verwirft Sitzung und Kopplung und kehrt zum Kopplungsbildschirm zurück. War es in diesem Moment nicht verbunden, arbeitet eine Station bis zur nächsten stillen Erneuerung ihrer Sitzung weiter (spätestens nach 15 Minuten) und fällt dann auf den Kopplungsbildschirm zurück. Alles, was fiskalisch signiert wird, wird sofort abgewiesen. Soll die Station augenblicklich stehen, starten Sie das Gerät neu.

Deaktivieren oder Widerrufen? Im Web-Admin unter Geräte → Terminals bietet das Detailfeld beides an, und die beiden sind nicht dasselbe:

  • Deaktivieren – sperrt das Terminal, bis es mit Reaktivieren wieder freigegeben wird. Das Terminal selbst mit TSE-Registrierung und Belegverlauf bleibt erhalten. Das Gerät verwirft jedoch seine Kopplung (siehe oben) und wird nach dem Reaktivieren mit einem neuen Kopplungscode wieder angebunden.
  • Widerrufen – löst die Gerätebindung. Das Gerät muss danach mit einem neuen Kopplungscode neu gekoppelt werden; das Terminal kann auch an ein anderes Gerät gegeben werden.

Ein Rollenwechsel wirkt dagegen sofort und kostet keine erneute Kopplung. Ändern Sie im Web-Admin die Rolle eines Terminals, meldet der Server dies dem Gerät: Es verwirft seine Sitzung, behält aber die Kopplung und meldet sich in der neuen Rolle wieder an. Eine Bestellstation holt sich dabei selbständig ihre Stations-Sitzung – niemand muss zum Gerät gehen oder einen Kopplungscode eintippen.

Statt „Abmelden" bietet die Station im Menü die Aktion Gerät neu koppeln. Sie setzt das Gerät auf den Kopplungsbildschirm zurück – der Weg, ein Gerät an einen anderen Platz zu geben oder es aus dem Betrieb zu nehmen. Zusätzlich steht, wie an der Kasse, die Aktion Backoffice öffnen bereit.

Abmeldung

Tippen Sie unten in der Navigationsleiste auf Abmelden (auf Telefonen auch unter Einstellungen → Allgemein → Konto). Der Aktualisierungstoken wird damit serverseitig widerrufen; der Zugangstoken läuft nach spätestens 15 Minuten ab. Die Kopplung des Geräts bleibt bestehen – die nächste Person meldet sich einfach an.

Im Web-Backoffice widerruft Abmelden (Benutzermenü) die Sitzung ebenfalls serverseitig. Ist der Server gerade nicht erreichbar, meldet das Backoffice Sie nach höchstens fünf Sekunden trotzdem im Browser ab; der Aktualisierungstoken verfällt dann regulär. Ein Neuladen der Seite zeigt danach wieder den Anmeldebildschirm.

Das Benutzermenü unten links im Web-Backoffice nennt die Berechtigungsgruppe der angemeldeten Person (z. B. Prüfer), nicht ihre Grundrolle – maßgeblich für die Rechte ist die Gruppe. Nur wenn der Server keine Gruppe meldet, erscheint die Rolle. Ist einem Konto keine Berechtigungsgruppe zugewiesen, wird die Anmeldung mit einem Hinweis abgelehnt („Ihrem Konto ist keine Berechtigungsgruppe zugewiesen“); eine Administratorin oder ein Administrator muss zuerst eine Gruppe zuweisen. Endet eine Sitzung ohne Abmeldung (abgelaufen oder beendet), weist der Anmeldebildschirm einmalig darauf hin.

Sicherheitshinweis: Melden Sie sich immer ab, wenn Sie das Gerät verlassen. Nicht abgemeldete Sitzungen können von anderen Personen missbraucht werden.

Sitzungen & Token-Widerruf

Das System verwendet kurzlebige Zugangstokens und langlebige, serverseitig verwaltete Aktualisierungstokens. Alle aktiven Sitzungen werden in der Datenbank erfasst und können gezielt widerrufen werden.

Zugangstoken (Access Token)
Kurzlebiges JWT (~15 Minuten, konfigurierbar über JWT_ACCESS_TOKEN_EXPIRY_MINUTES). Wird bei jedem API-Aufruf geprüft, aber nicht serverseitig gespeichert.
Aktualisierungstoken (Refresh Token)
Langlebig (~30 Tage), serverseitig in der Tabelle refresh_tokens gespeichert. Bei jeder Nutzung wird ein neuer Token ausgestellt (Token Rotation). Das Einreichen eines bereits rotierten Tokens löst Missbrauchserkennung aus und widerruft alle Sitzungen des betreffenden Mitarbeiters.
Automatischer Tagesreset
Einmal täglich (Standard: 04:00 Uhr, konfigurierbar) werden alle Aktualisierungstokens widerrufen. Alle Benutzer müssen sich beim nächsten Zugriff neu anmelden. Die Uhrzeit kann im Web-Admin unter System → Einstellungen → Sicherheit & Sitzungen eingestellt werden.
Sofortiger Sitzungsabbruch (Panic-Funktion)
Administratoren können im Web-Admin unter System → Einstellungen → Sicherheit & Sitzungen die Aktion „Alle Geräte jetzt abmelden" ausführen. Dadurch werden sofort alle aktiven Aktualisierungstokens aller Mitarbeiter widerrufen.
Automatischer Widerruf bei sicherheitsrelevanten Änderungen
Folgende Ereignisse widerrufen automatisch alle Sitzungen des betroffenen Mitarbeiters:
  • Passwortänderung
  • PIN-Änderung
  • Deaktivierung des Mitarbeiterkontos

JWT_DEVELOPMENT_MODE Muss in Produktion auf false gesetzt sein. Auf true nur für lokale Entwicklungsumgebungen. Ja (false)
JWT_ACCESS_TOKEN_EXPIRY_MINUTES Gültigkeitsdauer des Zugangstokens in Minuten. Standard: 15. Nein
Wichtig: Setzen Sie JWT_SECRET auf einen langen, zufälligen Wert (mindestens 32 Zeichen). Verwenden Sie niemals den Entwicklungsstandard in Produktionsumgebungen.

Diese Prüfung läuft als erster Schritt des Serverstarts, noch bevor die Datenbank gestartet oder migriert wird. Ein Start, der mit Refusing to start: … abbricht, hat die Datenbank also nicht verändert – Sie können die Konfiguration korrigieren und erneut starten.
