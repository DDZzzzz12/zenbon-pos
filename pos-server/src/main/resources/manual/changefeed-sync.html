1. Überblick

Das Change-Feed-Modell synchronisiert Referenz- und Konfigurationsdaten (Produkte, Kategorien, Extras, Choice Groups, Zahlungsarten, Tische und Raumelemente, Shop-Info, Shop-Konfiguration, Öffnungszeiten) zwischen Server und Kassen bzw. Bestellstationen. Es ersetzt den alten Timestamp-basierten Sync-Pfad vollständig.

Kernprinzip: SSE data_change ist nur ein Hint — der autoritative Feed ist GET /api/changes?since={seq}. Clients verfolgen einen einzigen lastSeenSeq-Cursor. Deletes sind erstklassige Feed-Einträge.

2. Der globale Sequenz-Cursor

Jede Änderung wird als Zeile in der entry_log-Tabelle gespeichert. Die Spalte entry_log.id (auto-increment BIGINT) fungiert als globale Sequenz. Clients speichern den zuletzt gesehenen id-Wert als lastSeenSeq und fragen den Server nach Einträgen größer als diesem Wert.

Warum keine Zeitstempel? Der alte Pfad nutzte WHERE updated_at > lastSyncTime mit Client-Uhrzeit als Cursor. Ist die Clientuhr schneller als der Server, werden Zeilen im Skew-Fenster dauerhaft übersprungen (stille Datenverluste). Die id-basierte Selektion ist uhrzeitunabhängig und korrekt.

Sichtbare Typen (clientSynced)

Nur Entitätstypen mit clientSynced = true in ChangeEntityType erscheinen im Feed. Audit-only-Typen (z. B. EMPLOYEE, VAT, TERMINAL) werden herausgefiltert.

Endpunkt Parameter Beschreibung
GET /api/changes since (Long, default 0)
limit (Int, default 500, max 1000)
Berechtigung SYNC_READ		 Gibt alle client-synced Einträge mit id > since zurück, aufsteigend nach id. Enthält auch highWaterSeq und minAvailableSeq für Cursor-Management und Fallback-Erkennung.
GET /api/entry-logs/paginated Filterparameter (type, operation, entityId, fromDate, toDate, page, size)
cursor (optional, opak) für Keyset-Pagination		 Paginiertes Prüfprotokoll für die Audit-Log-Ansicht im Web-Admin (Berechtigung AUDIT_READ). Separater Pfad — nicht für Sync-Zwecke verwendet. Antworten enthalten nextCursor; wird dieser als cursor zurückgegeben, ignoriert der Server page und blättert per (created_at, id)-Keyset (konstante Kosten auch bei tiefen Seiten).

Response-Format GET /api/changes

{
  "entries": [
    { "seq": 42, "entityType": "PRODUCT", "entityId": "17", "operation": "UPDATE" },
    { "seq": 43, "entityType": "PRODUCT", "entityId": "5",  "operation": "DELETE" }
  ],
  "highWaterSeq": 43,
  "minAvailableSeq": 1
}

highWaterSeq: der neueste seq-Wert des Servers (nur client-synced, non-ERROR Zeilen). Der Client setzt lastSeenSeq = highWaterSeq nach einem vollständigen Full-Sync oder wenn entries geleert wurde.
minAvailableSeq: älteste noch vorhandene Zeile in der Tabelle. Ist lastSeenSeq < minAvailableSeq, hat der Client History verloren und muss einen Full-Sync durchführen.

4. SSE-Benachrichtigungen

Live-Daten laufen seit v1.1.0 über Server-Sent Events (SSE); die frühere WebSocket-Verbindung gibt es nicht mehr. Der Server sendet data_change-Ereignisse über den Kanal GET /api/notifications/stream (text/event-stream, Berechtigung NOTIFICATION_READ). Diese Ereignisse sind nur Hints — sie teilen dem Client mit, dass Daten verändert wurden. Der Client ruft daraufhin GET /api/changes?since={lastSeenSeq} auf, um das Delta zu laden. Die im Ereignis mitgeschickte seq ist derzeit immer 0; maßgeblich ist allein der Feed.

  • Alle Clients erhalten das Ereignis, auch der Originator der Änderung — er muss seinen lokalen Zwischenspeicher ebenfalls aktualisieren.
  • Alle 15 Sekunden sendet der Server einen Ping-Kommentar, damit die Verbindung offen bleibt.
  • Beim Wiederverbinden schickt der Client den Header Last-Event-ID; der Server spielt verpasste Ereignisse aus einem begrenzten Puffer nach, bevor der Live-Strom beginnt. Was über den Puffer hinausgeht, holt der Client über den Feed nach (siehe Reconnect).
  • Werden die Sitzungen eines Mitarbeiters widerrufen, schließt der Server dessen Strom.

5. Reconnect & Fallback

Beim Wiederverbinden sendet der Client seinen aktuellen lastSeenSeq und führt einen Seq-Delta-Abruf durch:

  1. Abrufen von GET /api/changes?since={lastSeenSeq}
  2. Wenn minAvailableSeq > lastSeenSeq: History-Lücke erkannt → Full-Sync ausführen
  3. Sonst: Delta anwenden (Upsert + Delete)
Full-Sync vs. Delta: Der Full-Sync lädt alle Entitäten neu und setzt lastSeenSeq = highWaterSeq. Der Delta-Pfad aktualisiert nur geänderte Entitäten und setzt lastSeenSeq auf den größten seq-Wert im empfangenen Batch.

6. Retention

Die entry_log-Tabelle wächst kontinuierlich. Der EntryLogRetentionJob löscht Zeilen, die älter als das konfigurierte Retention-Fenster sind (Standard: 90 Tage). Die Retention ist opt-in und wird über den Scheduler-Mechanismus ausgelöst.

Clients, deren lastSeenSeq unterhalb des minAvailableSeq-Wertes liegt (weil alte Zeilen gelöscht wurden), erhalten beim nächsten Reconnect ein Full-Sync-Signal.

7. Gelöste Probleme des alten Modells

Problem Altes Modell Neues Modell
Uhr-Skew (clock skew) WHERE updated_at > clientCursor — Zeilen im Skew-Fenster werden dauerhaft übersprungen WHERE id > sinceSeq — Uhrzeit irrelevant, keine stillen Datenverluste
Deletes nicht propagiert Nur via Full-Sync (checkLogForDeletingData) Deletes sind erstklassige Feed-Einträge mit operation=DELETE
Full-Sync bei jedem Reconnect Flaky Wi-Fi → wiederholter Full-Sync aller Entitäten Seq-Delta-Abruf; Full-Sync nur bei nachgewiesener History-Lücke
TOCTOU-Stempel Cursor-Timestamp am Ende des Syncs gesetzt — Änderungen zwischen Query und Stempel werden übersprungen Cursor ist ein stabiler seq-Wert; atomare Zeilen können nicht „zwischen“ zwei Abfragen fallen
